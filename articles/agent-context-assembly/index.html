Agent 这一轮该带哪些上下文

  • 上下文管理
  • 状态管理
  • 权限控制
本文目录
  • 先分清哪些内容需要刷新

员工先问“上海住宿能报多少”，后来补了一句“我是上个月去的”。这时应该重新按出行日期查制度。即使上一轮的答案说得很清楚，把它连同几页现行制度一起传给模型，也容易让模型沿用原来的结论。

我倾向于把上下文组装做成单独一步。每次调用前都能回答三个问题：本轮要完成什么，哪些信息有权使用，放不下时先舍掉什么。

先分清哪些内容需要刷新

内容 这一轮怎么取
任务字段 从状态读取已确认的地点、日期和待补信息
身份与权限 由服务端按当前调用者和资源校验，模型只收到完成任务所需的字段
知识片段 按问题与适用日期检索，带回来源和版本
历史与偏好 保留理解指代所需的消息，其他内容按需读取
工具定义 按当前阶段和权限提供，执行前仍要鉴权

会话摘要可以保留“用户问过差旅报销”。具体是哪次出差、用户后来更正了什么，应留在可追溯的任务字段里。下一轮发现日期改了，就重新查证据。旧的摘要即使还留着，也不能替代重新查询。

放不下时，先裁哪里

先按实际接口计算输入预算，并给输出留空间。工具定义、历史消息和工具返回都会占用输入，图片的计量还取决于供应商和请求配置。可以先去掉重复证据，裁剪无关字段，再压缩较早的历史。裁剪证据时，保留结论所依赖的适用条件和原文引用。工具调用消息和返回消息要成对处理，避免裁完之后请求结构不合法。

如果一条制度的限制条件在另一页，单独留下结论段会改变原意。碰到这类问题，我会优先保留相邻证据，或者改成按页取需要的内容。关键证据仍放不下时，可以缩小查询范围或让用户补充条件。把半截证据塞进窗口再让模型猜，后面很难补救。

有些接口支持前缀缓存，可以把相对稳定的说明放前面。具体能否命中取决于供应商规则和输入是否满足条件，应用仍应组装本轮所需的消息。若复用历史摘要或检索缓存，还要处理改口、撤权和资料更新。 Anthropic 上下文工程说明

组装也要单独验收

我会拿同一个任务做三次小改动。先把日期改成历史日期，再撤掉一个来源的访问权，最后把工具结果换成超长数据。逐次检查实际请求，确认旧证据没有混回来，必要字段没有被截断，访问受限的片段没有进入模型。这样能先判断问题出在组装还是生成。
