一个 Agent 能在演示环境查资料、调接口，说明核心能力基本可用。要交给企业员工长期使用，还得回答另外一组问题：任务受理后重启会怎样，外部操作超时是否会重复，用户离职后权限多久失效，哪个版本的规则导致了这次结果。

对大多数已有业务系统的团队，我更建议从模块化应用、独立任务 worker 和可靠数据库起步。把模型用于理解、检索和局部决策，把任务生命周期、授权和业务提交留在确定的程序边界内。只有隔离、吞吐或团队协作确实需要时，再拆服务。

一、先约定业务范围与运行目标

以内部差旅助手为例，第一阶段提供制度查询、行程草案和申请准备；经明确授权后调用现有系统提交申请，审批仍由原审批系统完成。它不自行修改制度，也不把聊天里的“可以”直接解释成对任意后续动作的长期授权。

设计前至少需要确认这些条件：

事项 应明确的内容
用户与隔离 面向哪些员工，是否多租户，哪些数据需要更强隔离
任务规模 峰值并发、工具调用量、最长任务时间、人工等待时间
时延 受理、普通问答、长任务分别允许等多久
一致性 哪些状态必须先落盘，哪些信息允许最终一致
恢复 已受理任务允许丢失多少，故障后希望多久恢复
成本 单次成功任务预算、每个租户额度、人工接管成本
数据 模型和工具可处理哪些信息，日志和备份保留多久

可以先为受理接口设定一个待验证的目标，例如 p95 在 500 毫秒内返回任务编号；问答和执行另设完成时间目标。这个数字只是设计输入，不能当作架构已经达到的能力。受理速度快，也不代表排队中的任务很快完成。

受理层处理登录身份、租户、请求去重和任务创建。任务管理层处理调度、期限、取消、恢复和终态。Agent 运行层负责当前业务步骤中的理解、查询和工具选择。工具网关检查实际资源权限、参数和副作用，业务 API 维护自己的业务不变量。

知识检索和记忆可以独立成模块，但必须接受可信身份上下文。模型可以提出“查询某个申请”，不能自行决定该申请属于哪个租户、当前调用者是否有权读取。

配置发布、评估和运维形成另一条管理路径，管理模型配置、提示词、工具定义和流程版本。不要在每次请求中重新读取一套不断变化的全局配置，使同一个任务执行到一半突然换规则。

三、先让任务有可靠的生命周期

前台对话连接不能承担任务生命周期。浏览器断开，不代表后台任务取消；浏览器重新发送，也不代表用户想再创建一个相同申请。

受理时，在同一数据库事务中创建任务与 outbox 事件，再返回任务编号。后台可靠投递到队列，worker 领取任务后执行。这样可以避免“返回已经受理，但进程在入队前崩溃”的空档。消息仍然可能重复，消费端必须去重。AWS 事务发件箱模式

任务状态可以包括：已创建、排队中、执行中、等待用户、等待审批、结果核对中、成功、失败、已取消和已过期。状态名称可以调整，但每一种终态都要有明确业务含义。

“结果核对中”值得单独保留。调用外部提交接口超时，结果可能已经发生；在核对完成前，既不能显示成功，也不能显示“完全没有执行”。若核对本身到期，可以结束自动处理并转交人工，但操作记录仍须标明结果未知。

每个任务保存流程版本、状态版本、截止时间、当前步骤、证据引用和已发起操作。worker 通过租约和版本条件更新避免并发推进；租约过期后的旧 worker 可能仍在运行，还需要 fencing token 等机制拒绝其过期状态提交。它只能约束配合校验的组件，不能单独阻止外部 API 已经发生的副作用。

人工等待不应一直占着模型连接。先持久化等待状态，释放 worker，收到可信回调后再恢复。等待期间设置期限，明确过期、撤回和业务对象已变化时如何处理。

四、把外部操作当作独立的一致性问题

检查点保存的是运行状态。外部业务系统是否接受了操作，是另一件事。LangGraph 的容错文档也明确提醒：缺少本地确认应视为结果未知，需要向外部系统核对。LangGraph 容错与幂等边界

对于提交申请、发送通知、创建订单等动作，应先生成稳定的业务操作编号并持久化。相同意图的重试使用相同编号，用户确实发起新操作时才创建新编号。不要每重试一次就生成一个随机幂等键，也不要只用自然语言相似度判断两个操作是否相同。

幂等记录至少关联租户、操作编号、目标资源、规范化参数摘要和处理结果。相同编号却传入不同参数，应该拒绝并要求重新确认。下游需要真正支持并发去重，并提供状态查询，或在同一键重放时返回可核对的结果；网关里写一个“已执行”标志，并不能原子地覆盖远端提交。AWS 幂等 API 设计

还要核对下游幂等键的保留期限，覆盖允许的重试、排队和恢复窗口。超过期限后，同一键也可能被视为新请求，不能继续盲目重放。远端返回“已受理”只代表进入处理流程，任务要达到业务完成条件后才能标记成功；处理中和结果未知分别保留状态。

如果下游不支持幂等或查询，自动重试就要收窄。可增加业务侧适配层，或者把不确定结果转人工核实。单个 worker 串行执行能减少并发重复，但无法消除“远端已提交、本地未记录”的故障窗口。

跨系统流程常需要补偿，但补偿是一个新的业务动作。已经发出的通知收不回，已经生效的修改未必允许直接反向操作。补偿也需要权限、幂等和自己的失败处理，不能把数据库回滚的概念直接套到整个 Agent 任务上。

五、审批要绑定一个具体动作

用户点击确认时，应能看到目标对象、主要参数和预期影响。服务端保存审批人、权限范围、操作编号、参数摘要、业务对象版本、审批期限和必要的规则版本。

恢复执行前，检查审批是否还有效、当前身份是否仍有权限、对象是否已经被修改、参数是否变化。规则版本更新后，应判断它是否影响原操作的可执行性；影响时重新评估或审批。不要让模型自行解释旧的“同意”能覆盖新的内容。

在 LangGraph 中，动态中断恢复时会重新进入所在节点。因此审批前的代码可能再次执行。把审批和实际写操作拆开有助于管理，但写操作仍然要支持幂等，不能因为它放在审批之后就认为不会重复。中断与副作用说明

六、把权限落实到工具，而不只落实到入口

入口登录只是开始。工具网关每次调用还要校验操作类型、资源归属和当前权限，限制参数长度、查询范围和返回大小。模型生成的 SQL、URL、文件路径和命令，都属于待验证输入。

数据查询优先使用受控参数和命名接口。确实需要生成查询时，使用只读账户、允许的表与字段、行级隔离、超时和结果上限；语法正确并不代表语义安全。代码执行和浏览器操作放在隔离环境中，限制网络与文件访问，凭证由执行环境按最小权限提供。

MCP 可以统一工具连接与调用方式，接入之后仍需要具体工具的授权、凭证隔离和输出校验。它不会替企业完成业务权限判断，也不会自动让工具变成幂等接口。能力重叠时的取舍见Skill 与 MCP 选择文章。

外部文档、工具返回和用户上传内容都可能包含诱导指令。模型可用于识别可疑内容，确定性的权限检查和能力限制仍然需要存在。高影响写操作的开关，应由策略与授权控制，不能由检索到的文字打开。

七、超时、重试和降级要分层负责

给任务设置总截止时间，再给模型、检索和工具分配单次预算。重试消耗同一份总预算。对于限流和暂时性网络错误，可以在安全重试的前提下使用退避和随机抖动；参数错误、权限拒绝通常需要修正输入或停止。AWS 超时与退避实践

一个外部调用由 SDK、图节点和任务队列各重试几次，实际次数可能成倍增长。要明确哪一层负责哪一种失败，统一记录总尝试次数，避免多层同时无限恢复。

故障 可接受的处理
模型不可用 切换经过验证的备用模型，或保留任务稍后继续
检索不可用 告知依赖不可用；依赖制度的动作暂停
记忆不可用 不带偏好回答，或询问用户；执行依据缺失时停止
检查点写入失败 不继续推进需要恢复保障的外部动作
队列积压 限制新任务、提示预计等待、按租户公平调度
工具超时 先判断是否可能产生副作用，再决定重试或核对
用户取消 停止未开始工作，核对已提交和在途动作

备用模型也可能在工具调用格式、上下文容量和输出质量上不同。切换前完成兼容性验证，不能把所有模型都当作可以随时互换的字符串配置。

八、保留足够证据，才能定位错误

一次任务应能关联请求、执行步骤、检索证据、模型与提示词版本、工具参数摘要、审批、外部操作编号和最终结果。记录的是可观察的输入输出与决策依据，不要求保存模型完整的内部思考过程。

日志默认脱敏，正文、凭证和受限资料不应无差别进入监控平台。需要详细轨迹时，设置访问范围和保留期限；审计记录可以与调试日志分开保存，避免为了排查问题扩大数据暴露面。

重点指标包括任务成功率、超时率、人工接管率、重复副作用、结果未知的积压量、知识版本延迟，以及每次成功任务的总成本。除了接口是否返回 200，还要检查业务目标是否完成。

九、发布和恢复要使用同一套版本思路

流程代码、提示词、工具契约、模型配置、检索索引和状态 schema 都可能影响行为。发布时保存兼容的版本组合，记录每个任务实际使用的版本；知识与权限是否需要刷新则按业务时效策略单独处理。

旧任务可以继续由旧版本 worker 处理，也可以经过显式迁移后交给新版本。不要默认把旧检查点加载到新图里就一定能继续。改动中断顺序、状态字段或节点含义，都可能改变恢复行为。

回滚代码也不会撤销已执行的外部操作。离线重放和故障演练应使用隔离环境或替身工具，默认禁止对真实系统重复写入。备份需要演练恢复，并验证删除标记、权限版本和未完成操作记录一并恢复。

上线前至少演练：受理后崩溃、远端成功但本地超时、重复投递、审批期间撤权、旧 worker 晚到、新旧版本交替、取消后外部回执才返回。检查最终业务状态，而不是只看任务有没有重新跑起来。

十、用几个架构决策控制复杂度

决策记录 当前选择与原因 代价与重新评估条件
ADR-01 部署形态 模块化应用加 worker，减少初期服务边界 独立扩缩容、数据隔离或团队发布冲突明显时拆分
ADR-02 状态归属 业务库保存任务和操作事实，检查点保存运行状态 需要维护两者映射，恢复时以业务系统核对结果
ADR-03 自动化边界 确定流程管理提交，局部 Agent 处理理解和探索 灵活性较低，验证证明有收益后再扩大自治范围
ADR-04 数据存储 已有关系库与对象存储起步，检索能力按需增加 向量规模和过滤负载超出能力后再拆专用检索
ADR-05 人工介入 按动作风险、授权范围和异常状态设置入口 增加等待与运营成本，持续观察接管原因

企业架构没有一张适用于所有团队的最终图。第一版需要做到的是：受理有记录，执行有边界，失败能核对，版本能追溯，人工接得住。达到这些条件，再用真实负载决定下一次拆分和扩容，比从一开始堆满基础设施更容易长期维护。
