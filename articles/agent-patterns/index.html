Agent 架构与选型

从业务场景选择 Agent 的七种工程模式

给 Agent 选型，先问任务怎么完成，再问用什么框架。一个只需要查制度的助手，和一个要调查故障、修改配置、等待复核的助手，即使用同一个模型，运行方式也会差很多。

“Agent 有七种类型”没有统一的行业口径。有人按自治程度分，有人按推理和行动方式分，也有人把单 Agent、多 Agent、RAG、反思放在同一张图里。它们讨论的是不同维度，不能直接当成互斥的产品类别。

这里选取七种常见的工程组织方式：固定工作流、路由分流、并行处理、工具循环、规划执行、主从编排、评估改进。它们可以组合。固定工作流也不一定属于严格意义上的自主 Agent，但经常是企业 Agent 系统最合适的外围结构。

一、先把五个条件问清楚

第一，步骤能不能提前确定。发票字段提取、格式校验、结果入库，通常可以写成固定流程；调查一次未知故障，需要根据新证据决定下一步。

第二，任务能不能独立拆开。三个地区的资料可以分别查；三个模块同时修改同一个订单，通常不适合直接并行。能拆成三个标题，不代表能拆成三个独立执行单元。

第三，结果怎样验证。格式是否正确可以程序检查，接口是否正常可以运行测试，研究结论则需要核对证据。没有验证办法时，增加一个“审核 Agent”也可能只是多生成一份看起来合理的意见。

第四，错误能造成多大影响。查错一个公开产品参数和误改一个生产配置，应该走不同的工具权限、执行边界与确认流程。

第五，用户能等多久、一次任务能花多少。不要只统计一次模型调用的耗时。检索、工具调用、排队、重试和人工等待，都会影响最终体验。

Anthropic 的早期工程文章把预定义代码路径的 workflow 与模型动态控制过程的 agent 区分开来。这个区分仍然有用：能用确定流程完成的部分，通常值得保留为确定流程。Building effective agents

二、七种模式各自适合解决什么问题

1. 固定工作流：顺序已经清楚，让程序管住步骤

典型流程是“读取文档 → 提取字段 → 校验 → 人工处理异常 → 入库”。模型负责识别和生成，程序负责顺序、分支和业务校验。

适合结构明确的文档处理、制度问答、内容初稿和规范化数据转换。它的优点是容易定位失败发生在哪一步，也容易限制调用次数。

边界在于输入变化较大时，固定路径可能覆盖不了。遇到不支持的文件、未知字段或无法校验的值，应进入异常分支；不能为了维持流水线畅通，要求模型把所有输入都解释成合法结果。

客服场景可以把两种做法放在一条流程里。订单状态由接口查，模型可以把结果转成用户看得懂的话。投诉分支也可以让模型起草，但两条分支都要过发送前校验。分类拿不准时先澄清或转人工。需要处理退款时，由业务流程核对资格和审批，分类结果只用来选择处理入口。

2. 路由分流：不同问题走不同能力入口

比如员工服务入口先判断是设备故障、报销问题还是人事咨询，再交给对应流程。分流后可能是规则程序、检索服务，也可能是专门的 Agent。

适合领域之间知识、权限或工具差别比较大的场景。明确的业务字段可以先用规则路由，只有自然语言歧义较大时才需要模型参与。它并不要求每个分支都部署一个独立服务。

要预留“无法判断”和“同时涉及多个领域”的情况。用户问“新员工出差的电脑和报销怎么办”，不应该被迫只归入一类。可以拆成两个受控子任务，或先询问最影响后续流程的条件。路由结果也不授予访问分支工具的权限，实际调用仍需鉴权。

3. 并行处理：子任务互不依赖时，同时做

一份产品评估要查功能、价格条款和部署要求，可以分别取资料，再按统一结构汇总。多个独立检查器也可以同时检查格式、引用和敏感信息。

并行主要改善可独立工作的等待时间，或者增加互补的观察角度。它不会减少总工作量，往往还会增加调用和汇总成本。

要提前定义哪些分支必须成功、哪些结果允许缺失。某个关键分支超时，不能把其余分支拼成一份“完整评估”。多个模型结论一致也不能直接当作事实确认；它们可能共用同一份错误资料。涉及共享写入时，优先改成并行读、串行决策和受控提交。

4. 工具循环：根据一次结果，决定下一次行动

常见形式是“看当前信息 → 选择工具 → 读取结果 → 再决定继续还是回答”。例如排查某个 API 为何失败，先看错误，再查日志，发现配置问题后读取对应配置。

这类模式常与 ReAct 联系在一起。ReAct 论文讨论的是推理与行动交替进行的方式；现在的工具调用模型可以通过结构化工具接口实现类似循环，不需要要求模型公开完整的内部思考过程。ReAct 论文

适合路径有变化、工具数量和权限范围相对可控的任务。需要限制总轮数、重复调用和总期限，工具失败要返回明确状态。若相同输入连续得到同样的失败，系统应停止或转人工，不能让模型一直换措辞重试。

5. 规划执行：任务较长，需要显式管理依赖

比如“整理迁移方案，验证依赖，生成修改清单，再准备上线材料”。先形成可检查的计划，再按步骤执行；新证据说明原计划不成立时，更新剩余计划。

适合有多阶段依赖、用户需要看到进度，或者执行跨越多次会话的任务。计划至少包含步骤 ID、输入、依赖、完成标准和状态。它应该存在可持久化的结构里，而不是仅出现在模型的一段回答中。

计划只是待验证的安排。列出来不等于已执行，执行完成也不等于验收通过。计划变更不能把已经完成的外部动作假装撤销，更不能用新生成的操作编号重复提交旧动作。重规划次数也要受预算限制。

6. 主从编排：分工会随任务变化，需要协调者

先由协调者判断任务需要哪些子任务，再分配给执行单元，最后检查覆盖情况并汇总。例如调查某个行业问题时，不同问题可能需要完全不同的资料方向。

这与固定并行的差别，在于分工不是事先完全写死的。只有子任务需要独立的上下文、工具范围或探索过程时，独立 Agent 才更有价值。若子任务只是一个确定 API 调用，用函数或 worker 就够了。

主 Agent 要给出明确任务边界，子 Agent 返回证据、结果和未完成项，避免只交回一段摘要。还要限制子任务数量、嵌套深度和重复分工。Anthropic 的多 Agent 研究系统提供了一个研究场景实例，但其中的效果不能直接推广到共享状态密集的交易流程。多 Agent 研究系统实践

几个独立分支可以把结果写回共享状态，前提是明确谁写哪个字段、并发时怎样合并。要把对话交给另一个有独立权限的 Agent，则适合用显式交接，只带它能读、也确实需要的任务信息。比如查订单和处理投诉共用工单号即可，查订单时得到的收件地址通常无需跟着交接。

7. 评估改进：已有明确标准，允许有限返工

先生成结果，再检查，再根据具体问题修正。例如文档草稿生成后检查引用是否支持结论、接口变更后检查测试是否通过。

适合有可操作评价标准的任务。能用程序检查的先用程序，事实问题回到证据，风格问题再考虑模型评价。评估者最好返回具体失败位置和修改原因，避免只有一个模糊分数。

必须设置终止条件，例如通过硬性检查、没有可验证改进、达到迭代上限。模型自己评价自己可能重复同样的偏差；换一个模型也不能自动消除这个问题。高影响结论需要更可靠的外部验证，不能让两个 Agent 互相同意就算验收。

三、按场景建立一张初选表

下面是初始选择，不是固定答案。相同产品在不同阶段，可能需要不同组合。

业务场景 优先尝试的模式 为什么这样选 什么时候增加复杂度
员工制度问答 固定检索流程 来源明确，检索是必要步骤 需要跨制度核对并补齐条件时，加受控工具循环
发票信息整理 固定工作流 字段和校验规则较清楚 输入类型增多时加路由，低质量识别转人工
综合员工服务入口 路由分流 问题对应不同知识和工具边界 混合问题频繁出现时，增加拆解与聚合
跨地区产品调研 并行处理 地区信息可以独立收集 子任务方向无法预先确定时，加主从编排
只读故障调查 工具循环 下一步取决于中间证据 任务长且有清楚阶段时，加显式规划
代码或配置迁移 规划执行 有依赖、有阶段成果 可独立修改的模块多时，加隔离的子任务
文档或报告复核 评估改进 可以按规则和证据检查 达到固定轮数仍不合格时转人工
涉及外部提交的业务任务 固定状态机加局部 Agent 提交、审批和结果核对需要确定规则 自动化范围由验证结果和业务授权逐步扩大

客服、编程、研究描述的是用途；RAG 描述的是知识获取方式；单 Agent 和多 Agent 描述的是协作数量；反应式、目标驱动、学习型等分类又描述了不同的决策特征。因此，“用了 RAG”不能直接回答该不该多 Agent，“用了多 Agent”也不能回答需不需要规划。

这张图选的是主结构。权限、记忆、知识检索、人工介入和观测属于横向能力，每种模式都可能需要。不要把“需要审批”直接翻译为“必须上多 Agent”，审批首先是业务状态与授权问题。

五、框架放到下一层再选

只有几个固定模型调用，直接使用模型 SDK 加普通代码，常常更容易维护。需要标准模型与工具循环时，可以考虑 LangChain；需要显式控制状态、分支、中断和恢复时，可以考虑 LangGraph。两者的关系见框架选型文章。

若任务主要是跨服务的长时间业务流程，还要检查已有工作流系统能否承担调度、超时和恢复，再把 Agent 作为一个活动接入。不要让两个运行时都拥有同一层的重试和终态判断，否则同一次失败可能被反复放大。

选框架时看团队能否理解并接管执行状态，能否定位某个动作是谁发起的，能否在升级后恢复未完成任务。演示里少写十行代码，未必能抵消后续的运行维护成本。

六、用小规模对照实验决定是否升级

先从真实问题中选一批有代表性的任务，包含普通输入、复杂输入和历史失败。没有历史数据时，可以先手工构造小型验证集，正式上线后继续补充，不能把一批顺利演示当成稳定性证明。

保留最简单方案作为基线，只增加一个变量。例如先比较“固定检索”和“允许补查”，确认补查确实改善了复杂问题，再决定是否引入规划或多 Agent。不要同时换模型、提示词、检索和协作结构，最后却把效果全部归功于多 Agent。

需要观察的指标 具体看什么
任务成功率 是否满足业务验收，而非只生成了答案
错误动作与越权 是否调用了不该调用的工具或资源
成功任务成本 模型、工具、检索、重试与人工返工的总成本除以成功任务数
延迟 完成时间分布、排队时间、超时比例，人工等待单列
恢复能力 重启、断网和重复投递后能否正确继续
人工负担 需要补充条件、返工和接管的频率

并行任务的延迟接近关键路径耗时再加排队与汇总开销，并不等于所有分支耗时简单相加。成本则需要累计所有分支。多 Agent 可能更快，同时也更贵，两项指标应分开看。

先设硬性门槛，再比较收益。出现越权读取、重复提交或无法核对的业务结果，不能因为平均成功率高就接受。对于复杂度升级，至少要能说清楚它修复了哪一类失败，以及增加了多少延迟、费用和维护责任。

七、几个需要提前准备的退出分支

路由不确定时，允许澄清或进入通用入口；工具循环没有进展时，允许停止；并行缺少关键结果时，允许返回部分完成；计划不再成立时，允许重新规划剩余工作；评估改进到达上限时，允许带着明确问题转人工。

用户取消时，停止尚未开始的任务并请求取消在途任务，但已经提交到外部系统的动作要单独核对。主 Agent 超时也不代表子任务已经停止，调度层需要传播取消信号、控制任务租约，并处理晚到结果。无法确认是否发生过的外部动作应进入核对状态，而不是直接标记“已取消”。

选型的落脚点是一份具体判断：任务里哪些步骤固定、哪些需要探索，谁管理共享状态，谁能验证结果，达到什么条件必须停下来。把这些写清楚，再从七种模式中选主结构，后续框架选择通常就容易多了。
