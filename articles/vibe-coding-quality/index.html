Vibe Coding 的代码质量与长期维护

用自然语言描述需求，让 AI 写代码、修错误、补功能，确实能缩短从想法到可运行版本的距离。难点出现在几轮修改之后：为什么这样设计，哪些行为不能变，这次修复会不会影响另一个入口，下一位维护者还能不能接手。

这里把 Vibe Coding 理解为大量借助自然语言和 AI 生成、修改代码的开发方式。要用于持续维护的产品，需要把需求、代码差异、验证结果和发布记录连接起来。开发者可以少写一些代码，但仍然需要理解关键行为、维护约束，并对交付结果负责。

一、先区分原型阶段与长期产品

探索原型时，可以优先验证交互和技术可行性。一次性、无重要数据的实验，和已经承载用户资料、业务权限或生产流量的系统，投入的工程约束应当不同。

原型准备进入长期使用时，安排一次明确的整理：清理临时路径和硬编码，确认依赖来源，梳理数据模型，建立核心验证，补齐运行说明和责任人。不要把“能在当前机器启动”当成已经具备维护基础。

整理也不等于推倒重写。先找出需要长期稳定的边界，例如登录、权限、订单状态和文件存储，在边界外保留可调整的实现。每次只替换可验证的一部分，通常更容易控制风险。

二、把一句需求变成可验证的任务

“优化一下取消功能”缺少判断标准。更好的任务描述应当给出触发条件、预期行为、不适用情况和验证方式。

任务：允许用户取消尚未提交的申请。
正常行为：本人草稿可取消，列表显示已取消。
边界：已提交申请不能走此入口；他人的申请不可修改。
重复请求：第二次取消返回同一业务结果，不重复产生事件。
并发：取消与提交同时发生时，只允许一个合法状态转移成功。
验收：验证状态变化、对象权限、重复请求和并发结果。

这份说明同时约束实现和测试。AI 可以据此提出缺失条件，但不能为了容易通过验收，偷偷放宽原有行为或删除失败测试。

对于已有系统，先读入口、调用链和相关约定，确认现状。需求中的“当前行为”也可能记错，应以实际代码、业务规则和可复现结果一起核对。无法确定的条件先保留为明确问题，不用模糊实现把它掩盖过去。

三、让 AI 看到稳定的项目事实

仓库说明可以保持简短，集中写运行命令、目录职责、接口约定、数据来源、不可破坏的业务条件和必要检查。某个目录的特殊规则放到对应范围，详细设计放在独立文档，避免每次调用都加载一整本手册。

只写“注意质量”“遵循最佳实践”帮助有限。写清楚“权限判断由服务端执行”“申请状态只能通过指定服务转换”“公开接口不能返回内部字段”，更容易被检查。

自然语言约定用于解释意图，不能代替工具权限、类型检查和 CI。需要强制执行的规则，应放进编译、静态检查、权限配置或合并门槛。Claude Code 的工程建议也区分了说明性指令与需要确定性执行的检查。编码 Agent 的实践建议

上下文还要及时更新。已经删除的接口、旧的启动命令和过期架构图，会让 AI 很认真地沿着错误路径工作。把文档更新作为相关变更的一部分，内容以实际实现为准。

四、限制每次改动的范围

一次变更最好围绕一个可解释的目标：修复取消的并发问题，或者整理重复的权限判断。顺手改命名、换库、重排目录和调整 UI，会让评审者更难发现真正的行为变化。

开始前查看工作区已有改动，保留其他人的工作。完成后检查最终差异，确认没有无关文件、生成产物、密钥和大范围格式化。修改代码之后，AI 描述自己改了什么也可能不准确，最终以实际 diff 和检查结果为准。

当 Agent 反复在同一片代码里修了又坏，应先缩小问题、补充证据并回看设计。继续追加“再认真检查一次”，通常不能解决缺少业务约束的问题。

五、按风险设置几层验证

    B --> C[实现与局部验证]
    C --> D[类型 静态与安全检查]
    D --> E[关键行为与集成验证]

    F --> G[受控发布与观察]
    G --> H[反馈与维护任务]
    H --> A

基础层检查格式、类型和明显错误；业务层验证关键状态与权限；集成层核对数据库、外部服务和实际协议；界面变更还需要检查真实交互与布局。每一层都承担不同职责，不能用某一项通过代替全部验收。

变更 合适的重点验证
文案、样式、小范围布局 渲染与交互检查，相关构建
业务判断 正常、边界和明确的失败路径
权限与身份 跨用户、跨租户、失效凭证和拒绝路径
数据写入 约束、重复请求、并发和失败后的状态
外部 API 集成 契约、超时、部分成功与重试语义
数据迁移 旧数据、新旧应用兼容、恢复或前向修复

不必给每个低影响、可逆的修改增加大量测试。测试应帮助区分正确与错误行为，优先覆盖业务不变量、历史故障和代价较高的边界。只断言函数返回自己刚生成的固定文本，或者复制实现逻辑当作期望值，价值通常很低。

修复缺陷时，尽可能先确认一个能复现错误的案例，再验证修复后的结果。若测试只在新代码上运行过，至少要说明它为什么能识别原始缺陷，避免把“测试通过”误当成“问题已被证明修复”。

六、独立证据比模型互相同意更重要

同一个模型写代码再写测试，可能把同一个误解写两遍。可以让测试依据需求、接口契约、业务样例和历史错误构造，再用不同角色审查最终差异。换一个模型有助于增加观察角度，但不能保证判断独立。

AI review 适合查遗漏的异常路径、重复实现和契约不一致。高影响模块仍需能理解业务的维护者审查。GitHub 的 Copilot 文档也明确提醒，自动评审可能漏报或误报，需要核实反馈并补充人工评审。AI 代码评审的验证要求

检查失败时，先判断是实现、测试、依赖还是环境问题。测试被跳过、CI 没启动、外部服务不可用，都应记录为尚未验证。偶发失败要定位并治理，不能靠重复运行直到变绿掩盖不稳定性。

七、质量门槛放到仓库和流水线中

本地检查给开发者快速反馈，CI 提供统一环境。关键分支可以要求指定检查通过、必要人员评审，并防止未完成检查的变更直接进入。GitHub 的分支保护支持这些约束，但默认绕过权限和管理员适用范围仍需配置。受保护分支

CODEOWNERS 可以标明模块责任人，并结合合并规则要求对应人员批准。只放一个文件，不会自动阻止未经评审的合并。代码责任人机制

不能让 Agent 为了完成任务随意降低检查门槛。修改测试配置、权限规则或发布流程，应当作为明确的变更接受审查，说明原因和影响。未经信任的分支代码也不应在持有生产凭证的流水线环境里任意执行。

依赖文件和锁文件一起维护，验证包名、来源和实际用途。AI 建议的包可能不存在、同名或不适合当前项目。对构建产物保留来源与版本记录，有助于追查发布内容；SLSA 的来源证明可以增强供应链可追溯性，但不能证明业务逻辑正确。SLSA 规范

八、长期维护靠清楚的边界与责任

关注模块之间怎么依赖：业务规则集中到可测试的位置，基础设施通过明确接口接入，避免同一判断散落在页面、接口和后台任务里。为模型调用、检索和外部工具留出适配边界，升级时就能围绕契约替换，而不用修改整个系统。

抽象也要克制。两个相似函数不一定马上需要通用框架；如果它们的业务变化方向不同，强行合并反而更难维护。优先保留清晰命名和局部结构，出现稳定的重复模式后再提炼。

关键设计保留简短决策记录：解决什么问题，为什么这样选，有什么代价，什么条件下重新考虑。注释解释不直观的业务限制，运行说明保证其他人能启动、验证和发布。不要把与代码重复的自然语言堆满文件，当成可维护性。

每个模块要有人能接手。可以让 AI 整理调用链、辅助定位和生成修改，但最终需要有维护者知道关键行为在哪里、如何验证、失败后怎样恢复。一次任务结束时，把未解决问题和必要后续工作写清楚，避免只留一句“已完成”。

九、发布后继续验证真实行为

涉及重要行为时，小范围发布，观察错误率、关键业务结果和资源消耗。保留版本与变更记录，确保能关联到具体代码、配置和数据迁移。

数据库修改尤其要考虑新旧应用共存。可以先增加兼容字段、迁移数据、切换读写，再清理旧结构；具体步骤按数据规模和业务约束验证。回滚应用代码不等于恢复数据库，更不等于撤销已经调用的外部操作。

质量反馈不能只看生成速度和代码行数。可以观察变更后的故障、返工时间、同一模块重复缺陷、测试不稳定比例，以及新维护者理解一个改动需要多久。若生成越来越快，评审和修复越来越慢，就需要收紧单次改动范围、改善验证或调整架构。

NIST SSDF 强调把安全开发实践纳入整个开发生命周期。对 AI 辅助开发同样如此：发现问题后要处理根因，并把可重复的防护加入后续流程，而不只修复眼前的一行代码。NIST SSDF 1.1

十、交付时能给出这些证据，就比较扎实

能够说明需求对应哪些行为变化，最终改了哪些文件，运行了哪些必要检查，哪些边界已经验证，哪些检查因环境限制尚未完成。高影响变更还应给出发布观察方式、数据兼容策略和恢复路径。

这些信息可以很简短，不需要每次生成长篇报告。真正需要保留的是足以让下一位维护者判断“为什么可信、出了问题从哪里查”的证据。代码生成交给工具加速，工程约束落实到仓库、测试和运行环境中，长期维护才不会只依赖某次对话的上下文。
