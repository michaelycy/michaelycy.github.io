表头拖宽以后，表格内容为什么没跟上

发布于 2026年11月22日

把「客户名称」的表头向右拖一点，鼠标下面的边线跟着动了，第一行的客户名称却还挤在原来的宽度里。再横向滚动，表头和正文的列边界越来越难对齐。在开发者工具里各选一条边线，就能看见它们分属两张表。

我参与过的企业前端组件库里，当时使用的 Ant Design Table 在这个场景下分别渲染表头和内容区。我们用 react-resizable 接收尺寸变化、同步两边的单元格，后来把这段重复逻辑抽成了 Hook。

从 160 拖到 220，两个宽度在哪里分开

举个简化例子，客户名称原本宽 160 像素，拖动回调已经给出 220。如果回调只改当前表头单元格的样式，表头边线会到 220，正文用的列配置却还停在 160。短名称可能勉强能看，换一个较长的公司名，两边用的宽度就显出来了。react-resizable 的受控用法会把尺寸交给调用方，怎样用这次变化更新表格，由调用方处理。react-resizable 组件说明

把回调值、列配置和两张表上量到的宽度放在一起看。回调是 220、配置是 160，先沿着回调查哪一步丢了新值。配置已经是 220，表头和正文实测却相差一截，接下来要量两个容器的可用宽度，以及纵向滚动条占了多少地方。两种错位在截图上很像，差异出现的位置却能直接量出来。

尺寸同步进了 Hook，页面还要管什么

这段逻辑最初要解决的是同一次拖动怎样落到两张表上。把同步收进 Hook，复用的是从拖动回调到两边单元格更新的这段过程。页面仍然了解自己的列，比如「客户名称」允许拖宽，末尾的操作按钮要留足空间。业务页面换一组列，也能复用同一套同步处理。

用「编号、客户名称、负责人」三列就能看出这层分工。把客户名称拉到 220，再隐藏编号，客户名称就从第二列到了第一列。设计这类 Hook 时，可以按稳定的列标识记录调整后的宽度，再让表头和内容区读取这一列的结果。按显示位置记录，原来给第二列留的 220 就可能落到负责人身上。

验收时在同一个弹窗里先放三行短数据，再加到足以出现纵向滚动条。拖宽客户名称，隐藏编号，横向滚到最右边，然后切回三行。只有滚动条出现时整排偏开，就量两个容器。只有隐藏编号后某一列变宽，就查 220 最后跟着哪一个列标识。
