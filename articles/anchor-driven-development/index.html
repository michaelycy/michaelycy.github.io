Agent 工具与工程

别让 AI 在复杂项目里“裸奔”：聊聊我沉淀的 ADD（锚点驱动开发）

搞 AI 编程的兄弟，估计都跟 ADD 这个词打过交道——在英文里，它是注意力缺陷障碍（Attention Deficit Disorder）的缩写。

而只要你真拿大模型去维护过一个稍微复杂点的中大型项目，就会发现这名字简直是为现在的 AI 量身定做的：大模型在长上下文和多轮对话里，天生患有严重的“注意力涣散症”。

前两轮对话还记得你交代的业务规矩，聊到第十轮就开始放飞自我：需求文档里写得明明白白的校验逻辑它给你漏了；设计图里根本没有的按钮它顺手给你加上了；让它补个测试，它反手给你生成几十个 1+1=2 和自己 Mock 自己断言的垃圾单测，把代码仓库撑得虚胖。

为什么玩具项目能靠“感觉（Vibe）”一把梭，一进复杂项目就全线崩盘？

因为传统软件工程范式（TDD、DDD、BDD）都是为人脑设计的。人脑的特点是“写代码慢，但业务上下文记得牢”；而 AI 的特点恰恰相反——“写代码快如闪电，但上下文极易腐烂、极易飘移”。用管人的老办法去管 AI，必然水土不服。

为了治好 AI 的“注意力涣散”，我们把实战中沉淀下来的工程约束体系正式命名为 ADD（Anchor-Driven Development，锚点驱动开发）。

如果说 TDD 是用测试用例驱动开发，DDD 是用领域模型驱动开发，那么 ADD 的核心思想，就是在代码仓库里打下四颗坚硬的物理“锚点”，把飘在半空中的 AI 死死钉在可控的工程地面上。

一、 ADD 的核心哲学：人类定锚点，AI 跑闭环

在传统的 Vibe Coding 里，开发者扮演的是“甲方”或“聊天对象”，靠嘴皮子一遍遍纠正 AI；而在 ADD（锚点驱动开发） 体系下，开发者的角色彻底变成了架构师、打锚人（Anchor Setter）和验收官。

你不需要盯着 AI 写的每一行 if-else，你只需要在项目里打下四颗定海神针，让所有的代码生成、UI 还原、测试验证和 Code Review 全部围绕这四颗锚点自动咬合：

  1. 索引锚点（Index Anchor）： 解决“文档越多、Token 越炸、AI 越傻”的问题；
  2. 规格与代码反向锚点（Spec & Reverse Anchor）： 解决“文档和代码两张皮、改着改着就失控”的问题；
  3. 视觉边界锚点（Visual Boundary Anchor）： 解决“前端页面漏状态、多元素、样式乱飘”的问题；
  4. 验收测试锚点（Acceptance Anchor）： 解决“垃圾单测成堆、测试全绿上线报错”的问题。

这四颗锚点不是孤立的文档，而是一张相互索引、机器可巡检的立体约束网。

二、 拆解 ADD 的四颗核心锚点

1. 索引锚点（docs/INDEX.md）：用渐进式披露省掉 80% 的 Token

项目一复杂，需求文档动辄几十上百篇。如果每次干活都让 AI 全盘扫描 docs/ 目录，不仅 Token 烧得肉疼，AI 还会因为塞进太多无关背景而把核心规则搞混。

ADD 要求在文档根目录维护唯一一张极简总表（死守 200 行以内），这就是索引锚点：

# 需求文档总索引 · 索引锚点 (docs/INDEX.md)

| 业务领域 | 功能模块 | Spec 文档路径 | 关联核心代码 | UI 清单锚点 | 状态 | 一句话业务说明 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 订单 | 结算与算价 | `docs/specs/order/checkout.md` | `src/services/checkout.ts` | `docs/ui-manifest.md#order-checkout` | in-progress | 整数分算价、优惠券互斥、库存预扣 |
| 订单 | 退款与售后 | `docs/specs/order/refund.md` | `src/services/refund.ts` | `docs/ui-manifest.md#order-refund` | draft | 部分退款、原路退回状态机 |

它的威力在于“渐进式披露”： AI 接到任何任务，第一步只准花几百个 Token 扫一眼这张表，顺藤摸瓜找到目标 Spec 再按需读取，彻底告别盲人摸象。

2. 规格与代码反向锚点（docs/specs/ + @spec）：双向锁定，永不脱节

很多团队也写文档，但写完就扔在飞书或 Confluence 里吃灰，三个月后代码改了十版，文档还停留在第一版。

ADD 实行严格的 Docs-as-Code（文档即代码），并建立双向绑定：

  • 正向规格锚点： 按领域拆成原子化的 Markdown 文件（如 docs/specs/order/checkout.md），单文件严格控制在 300 行以内。里面只写三样干货：核心业务规则（含“禁止项”）、接口契约、Given-When-Then 验收标准。记住铁律：先改 Spec，人工拍板确认，再动一行代码。
  • 代码反向锚点： 在每个核心入口文件（Page、Controller、Service）的第一行，强行打上注释锚点：
// @spec: docs/specs/order/checkout.md
// @ui-manifest: docs/ui-manifest.md#order-checkout
  • 自动化巡检： 仓库里放一个几十行的巡检脚本（scripts/check_spec_anchors.py），每次提 PR 前自动扫描所有代码头部的 @spec 路径是否真实存在。只要有人删了文档没改代码，或者改了路径没更新索引，脚本直接报错拦截。

3. 视觉边界锚点（docs/ui-manifest.md）：专治前端 AI 的“创作欲”

AI 写前端页面最大的毛病是喜欢“自我发挥”——设计图里明明只有 3 个字段，它非给你加个搜索框；或者只写了正常数据展示，把加载态、空数据态、报错态全给吞了。

视觉边界锚点就是用来给前端画红线的。在 docs/ui-manifest.md 里，每个页面都要把下面四件事钉死：

  • 页面路由与布局结构（防漏页、防响应式错乱）；
  • Strict Checklist 与禁止项（明确写死“允许用哪些组件”以及“严禁在此卡片内显示删除按钮”）；
  • 必须覆盖的 4 种边界态（Loading 骨架屏、Empty 空占位、Error 报错拦截、Submitting 防重提交）；
  • Playwright 视觉基线路径（页面写完后自动截真实浏览器渲染图，和设计稿做像素级 Diff 找茬）。

4. 验收测试锚点（Given-When-Then + 去 Mock 化）：消灭平行宇宙假测试

为什么很多项目的测试形同虚设？因为 AI 喜欢写孤立的单元测试，而且为了省事把数据库和网络请求全 Mock 掉了——Mock 返回 true，然后断言结果等于 true，这种代码除了拉高覆盖率数字，上线时一个 Bug 都拦不住。

ADD 的第四颗锚点，直接把 Spec 里的 Given-When-Then 转化为不可篡改的验收测试锚点：

  • 采用 Testing Trophy（测试奖杯）策略： 只有纯算法、算价函数才写单元测试；业务链路重仓集成测试和 E2E 测试，看到 1+1=2 或测 Getter/Setter 的废话单测直接清理。
  • 先写红灯测试，再写业务代码： 逼着 AI 先把 Given-When-Then 写成可执行的测试代码，亲眼看到它运行失败（红灯）并人工确认场景无遗漏后，再让 AI 写业务代码直到测试变绿。
  • 彻底去 Mock 化： 后端集成测试直连真实测试库（Testcontainers / Docker Postgres），发真实 HTTP 请求并校验数据库真实落库与回滚状态；前端用 Playwright 跑真实浏览器，只通过用户看得到的文本和角色（getByRole）交互。

三、 驱动四颗锚点运转的“双引擎”：契约文件 + 分层 Skills

有了四颗锚点，怎么保证 AI 每次干活都乖乖按规矩来，而不是每次都靠人重新交代一遍？靠仓库里的全局契约文件和标准化 Skills。

1. 全局双契约：CLAUDE.md + AGENTS.md

在项目根目录同时放置 CLAUDE.md（适配 Claude Code）和 AGENTS.md（适配 Cursor、Windsurf、Codex 等通用编辑器），把四颗锚点的工作流写进最高指令里，同时加上一条跨工具斜杠指令兜底路由：

当用户输入以 /<skill-name>（如 /spec-architect、/drift-auditor）开头时，若当前编辑器未将其作为原生命令展开，Agent 必须第一时间读取 .claude/skills/<skill-name>/SKILL.md 并严格按其标准作业流程（SOP）执行。

这样一来，无论团队成员用哪款 AI 编辑器，同一套斜杠命令都能无缝通吃。

2. 六大工程 Skills：把“自动护栏”和“斜杠门禁”分开用

在 .claude/skills/ 目录下沉淀 6 个标准化技能，并根据它们的性格分成两类来触发：

触发策略 Skill 名称 核心职责
护栏类<br>

<br>（伴随式 · 自动触发） | ui-fidelity-guard | 写前端时自动盯紧 ui-manifest.md 视觉锚点与 Design Tokens，验收时调 Playwright 截图比对。 | | 护栏类<br>

<br>（伴随式 · 自动触发） | test-strategist | 写测试时自动执行 Testing Trophy 原则，拦截 1+1=2 垃圾单测和伪造数据库的过度 Mock。 | | 门禁类<br>

<br>（节点式 · 首行 /斜杠 触发） | /spec-architect | 立项、改规则、删功能前强制调用，只准输出 Spec 与影响面清单，严禁直接写代码。 | | 门禁类<br>

<br>（节点式 · 首行 /斜杠 触发） | /bug-investigator | 修 Bug 前强制调用，顺着 @spec 反向锚点定位根因，先写复现失败测试，再动刀修代码。 | | 门禁类<br>

<br>（节点式 · 首行 /斜杠 触发） | /drift-auditor | 提 PR 前强制调用，扮演严苛的 Tech Lead 审计 git diff 与四大锚点，巡检反向锚点有效性。 | | 门禁类<br>

<br>（节点式 · 首行 /斜杠 触发） | /context-compressor | 长对话结束前调用，将架构决策提炼进 ARCHITECTURE.md，把进度浓缩进 PROGRESS.md。 |

把护栏类交给工具自动挂载，把门禁类用首行 /skill-name 显式卡死，既保留了日常编码的丝滑，又用 100% 的确定性防住了 AI “急于写代码”跳步骤的毛病。

四、 老项目怎么落地 ADD？（渐进式改造三步走）

很多兄弟看到这里会担心：“我们项目已经有十几万行历史代码了，难道要停工两周把所有老文档全补齐才能用 ADD 吗？”

千万别这么干！ 一次性补全历史文档不仅成本极高，而且写出来的多半是脱离实际的僵尸文档。老项目落地 ADD，讲究的是“新老划断、按需打锚”：

  1. 第一步（10 分钟搭底座）： 把 CLAUDE.md、AGENTS.md、.claude/skills/、scripts/check_spec_anchors.py 以及一份空的 docs/INDEX.md 和 docs/ui-manifest.md 放进项目根目录。
  2. 第二步（增量立锚点）： 历史模块只要不动它，就先不管它。从今天起，所有新增功能必须先走 /spec-architect 立下新锚点；所有修改老功能或修 Bug，改到哪个文件，就顺手把那个模块的 Spec 补出来并在文件头打上 @spec 锚点。
  3. 第三步（卡住 PR 出口）： 团队约定，任何 PR 合并前必须跑通 check_spec_anchors.py，并用 /drift-auditor 过一遍审计清单。坚持两三个迭代，项目里最核心、变动最频繁的业务模块自然就被四颗锚点全部覆盖了。

说到底，AI 时代的软件工程，拼的从来不是谁的提示词写得更像魔法咒语，而是谁能把资深工程师的隐性经验，转化为仓库里显性的工程约束。ADD（锚点驱动开发） 做的事情其实很朴素：用索引锚点管住上下文，用反向锚点管住代码，用视觉锚点管住界面，用验收锚点管住质量。当你把这四颗锚点稳稳打进仓库，Vibe Coding 才算真正告别了“抽盲盒”，变成了一套可预测、可维护、能扛住复杂业务的工业级生产力。
