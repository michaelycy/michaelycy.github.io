PDF 译文校准的坐标转换与回写

在文档翻译工具里改版面，最让人头疼的错位通常是连环出现的：把一行译文往右拖一点，当前预览看着正好，缩放一下却偏了，等真正导出 PDF 打开，位置又跑了另一截。

这类问题如果只当成前端拖拽偏差去修，往往治标不治本。我们基于 Python 构建的文档翻译智能体，会把每一份文档送入一条七阶段流水线：解析 → 排版 → 识图 → 译图 → 渲染 → 优化 → 生成。译文校准并不是孤立挂在界面上的一个小功能，它精准卡在渲染与优化两个阶段之间——上游承接多个阶段产出的异构坐标，下游决定最终生成 PDF 能否做到“所见即所得”。

要让校准后的译文不偏移、不丢失，核心在于用一套统一的中间坐标模型把转换链路锁死，并把每一次人机协同的改动可靠地回写到数据层。

渲染阶段：把上游多源坐标归一到标准页坐标系

坐标之所以会在预览和导出之间“分道扬镳”，根源在于流水线上游天然存在多套互不兼容的坐标系：

  • 解析与排版阶段（PDF 矢量坐标）：遵循 PDF 原生规范，单位通常是磅（pt，72 DPI），常见左下角为原点；同时页面还可能带有 MediaBox 与 CropBox 的裁剪偏移，以及 /Rotate 旋转元数据。
  • 识图与译图阶段（图像像素坐标）：Python 侧通过图像处理和 OCR 拿到的是像素框（px），左上角为原点；如果原件是歪斜的扫描件，识图前往往还会经过去畸变或角度回正（Deskew），框的位置基于回正后的图片。
  • 校准工作台（视口显示坐标）：预览界面叠加了缩放比例、滚动偏移、设备像素比，甚至只局部渲染了页面的一部分。

如果直接拿其中某一套数字去覆盖另一套，任何缩放、旋转或裁剪都会立刻放大误差。

我们在 Python 后端的渲染阶段引入了标准页中间表示（Page IR）作为唯一基准坐标系。无论是解析提取的文本块，还是识图、译图产出的图文区域，在进入渲染阶段前，都必须通过显式的仿射变换矩阵归一到同一套标准页坐标中；渲染预览时，再由标准页坐标正向映射到编辑视图。

这里最容易踩坑的是把“缩放”当成全部变换。如果页面仅仅放大两倍且坐标轴方向一致，向右拖动 20 个像素，换回标准页坐标确实只需要除以 2。但一旦页面本身带有 /Rotate 属性或经历过扫描回正，屏幕上的“向右”可能对应原页坐标的向上甚至斜向。因此前后端传递和计算位置时，不能只传缩放比，必须严格维护完整的仿射矩阵及其逆矩阵，把裁剪偏移、旋转角度和缩放比例放在正确的层级里依次左乘。

逆变换里的隐蔽陷阱：扫描件回正后的外接框膨胀

当用户在预览界面拖动或缩放文字块时，后端通过逆矩阵把视图坐标还原为标准页坐标。普通矢量 PDF 做到这一步基本就稳了，但扫描件在“识图 → 渲染 → 优化”之间还藏着一个很容易导致重复漂移的细节。

假设一张歪斜的扫描页先做了 3 度回正，OCR 在回正后的图片上识别出了一个水平矩形文字框。如果校准后为了存回原图接口，我们把这个矩形反向旋转回原图坐标，再取一个能包住四个顶点的水平外接框（AABB），这个新框的面积一定会比原来大一圈。

问题在下一次打开编辑器时爆发了：如果系统再次读取这个变大的原图外接框，并重新做正向回正变换，预览框会再膨胀、偏移一次。每打开保存一轮，框就往外飘一点。

解决办法是在 Page IR 里把两种几何语义拆开保存，各司其职：

  • 规范化编辑框（Canonical Box）：保存在标准页（即回正后）坐标系下，专门用于渲染预览与二次打开校准，避免反复做外接矩形近似带来的精度退化。
  • 原始映射信息与像素框（Raw Box + Transform）：保留回正矩阵与原图坐标，仅供下游需要直接操作原图的抹除或贴图接口使用。

只要重绘预览时优先消费规范化编辑框，哪怕同一个扫描页反复打开微调十次，文字块的位置和大小依然纹丝不动。

优化阶段：人工校准与智能体自动优化的协同

在翻译智能体里，优化阶段承担着双重职责：一方面是智能体自动优化，另一方面是人工介入校准。

译文长度变化是绕不开的现实——原文一行紧凑的英文，翻成中文或德文后可能变成两三行，或者因为专业术语变长导致超出边框、遮挡相邻段落或图表。智能体在优化阶段会自动执行版面检查，针对溢出块做字号微调、行距压缩或重排避让。与此同时，用户也会在校准界面里顺手做叠加操作：先改两个译词，再把字号调小一号，最后把整个框往右挪一点。

要让“多次人工操作”以及“智能体自动优化与人工微调”不互相打架，回写链路必须解决两个工程问题：

1. 字段级解耦与增量合并

在 Page IR 中，每一个译文块的数据结构严格拆分为三个正交维度：

维度 包含字段 典型触发源
内容层（Content） 译文文本、分段换行 人工改词、智能体润色
样式层（Style） 字体、字号、字重、行距、对齐方式 人工调样式、智能体防溢出缩字号
几何层（Geometry） 标准页包围盒、旋转角、层级（Z-index） 人工拖拽缩放、智能体防遮挡避让

校准提交的不是“整块旧数据的全量覆盖”，而是带字段路径的增量补丁（Patch）。用户拖动位置时，只更新几何层字段，绝不会因为前端缓存了旧文本而把前一步修改的译词盖掉；反之，改完文字重新测算行数时，也会严格沿用当前最新的几何框与样式参数。

2. 人工锁定（Human-Override Locking）与职责分离

当用户手动把某个文字块挪到满意的位置，或者指定了字号后，IR 会为该块的对应维度打上 manual_locked 标记。之后如果邻近段落发生变动、触发智能体重新执行局部版面优化，智能体在计算重排和避让时，会把已锁定的块当作刚性约束（只避让、不移动、不改字号），避免系统“好心办坏事”，把人刚调好的版面又刷回原样。

同时，我们在排查问题时也把几何校准和版面检查彻底拆开：文字块整体位置跑偏，优先查仿射矩阵和坐标基准；位置精准但文字截断或叠字，则归入优化阶段的文本度量与排版逻辑，两者不再混为一谈。

从回写到生成：让“预览对齐”等于“导出对齐”

很多人理解的“回写”是直接去修改底层的 PDF 文件流，但在 Python 翻译智能体架构中，边拖拽边改 PDF 既慢又极易损坏原文档结构。真正的回写对象是结构化的 Page IR。

每一次校准确认后，Python 后端会校验增量 Patch 的合法性，将新的坐标、样式与锁定状态持久化写入 IR（支持直接覆盖当前任务版本，或基于当前快照另存新版本）。这一步本身是轻量级的数据更新，同时保证了任务在刷新、中断或重试时状态不丢。

当流程推进到最后一个环节——生成阶段时，Python 合成引擎不再依赖前端的任何截图或临时状态，而是完全基于定稿后的 Page IR 执行确定性合成：

  1. 坐标逆向还原：将 IR 中的标准页坐标，依据页面元数据（CropBox 偏移、/Rotate 角度与目标 DPI）精确映射回目标 PDF 的原生坐标系。
  2. 底图与原文清理：按几何层坐标对原 PDF 文本区域进行精准擦除或背景色填充；对于译图阶段产出的图片块，按对应映射关系将译后图像回贴到原位。
  3. 同源字体度量回填：Python 侧在渲染预览与最终生成时，复用同一套字体文件与行宽换行测算逻辑。按照样式层的字号、行距和几何层的包围盒，将译文重新绘制进 PDF 页面。

因为预览渲染和最终生成消费的是同一份标准页 IR 和同一套排版测算规则，所以只要渲染阶段的坐标变换矩阵闭合、优化阶段的增量回写无损，导出后的文件就能在普通页、旋转页以及回正扫描页上与校准视图保持一致。
