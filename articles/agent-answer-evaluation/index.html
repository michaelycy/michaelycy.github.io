Agent 答对了多少题，怎样从一次评测里看出来？

员工在预订页选中了一间每晚 620 元的酒店，问差旅助手：“我能先订，出差回来再补批吗？”助手答：“这笔费用需要负责人审批，记得保留票据。”假设公司的差旅制度规定，每晚不超过 500 元可以按常规流程预订，超出上限就要先拿到负责人的书面批准。员工听明白了要审批，还是不知道现在能不能点“预订”。

我们用这道差旅题跑一次评测，看看参考答案里的哪些条件该写进评分标准。比较新旧两版时，还得翻回这道题看一眼。即使新版的平均分涨了，它也可能把“先批再订”说成“先订再补批”。

每晚 500 元和 501 元，答案该差在哪里？

如果参考答案只写“需要审批”，开头那句回复很可能拿到高分。出题时，我会先请熟悉制度的同事替员工答一遍。这间房超了 500 元，要等负责人书面同意后再订。把这句话写进参考答案，验收的人就知道该查什么了。只提审批、漏了书面批准，或者把先后顺序说反，都能找到扣分的依据。

拿这条制度出题，可以每次只改一个条件。把房价从 500 元改成 501 元，看助手懂不懂上限。房价都写 620 元，只改成“已经获批”，看它会不会还让人去申请。

员工怎么问 怎样算答对
每晚正好 500 元，能按常规流程订吗？ 可以。500 元还在上限内。
每晚 501 元，还没拿到书面批准，现在能订吗？ 得先拿到负责人的书面批准。多出的这 1 元已经触发审批。
每晚 620 元，出差回来再补批行吗？ 要在预订前取得负责人的书面批准，回来再办就晚了。
每晚 620 元，负责人已经书面同意了，还要等这项审批吗？ 超标预订要求的书面批准已经拿到了，可以继续走预订流程。

在平台的评测集里，每道题占一行。问题填在 input，参考答案填在 reference_output。我会再加两列，记下适用条款和制度版本。哪天有人对 500 元那题的分数有疑问，顺着记录就能核对原文里的“不超过”。

题库里除了常见问法和边界题，还可以收录线上答错过的问题。去掉个人信息，留下触发错误的条件，改完助手后就能拿来复测。同一道题的几种改写要放在同一组。调提示词时用过“能不能先订”，验收时再拿“可以先下单吗”来考，很容易高估效果。最好另留一组调试时没见过的题。

这四道题可以手工录入。题多了就用 Excel 或 CSV 导入，先在预览里看哪些行有错、哪些重复。也可以选一个已发布的提示词和一个模型，让模型先出一批候选问答。人逐条看过、勾选，再提交成新版评测集。审核时值得多看一眼 500 元那行。模型只要把“不超过”写成“低于”，助手照制度答对，反倒可能被扣分。

一份回答，为什么要打两次分？

新建实验时，先选评测集版本和被测的 Agent，再选一个或多个评估器版本。然后配字段映射，指定每一列送给谁。跑 620 元这题时，把 input 里的问题交给助手。等它答完，再把实际回答、参考答案和适用条款交给评估器。如果把参考答案也填进助手的提示词变量，它答得再好，也很难看出它自己能不能读懂制度。

假设选了两个评估器，一个评业务结论，另一个评行动指引。普通 Agent 对每条样本单独回答一轮，两个评估器读同一份回复。四道题跑完，留下四份回答、八条评分。拿“需要审批，记得留票据”这句来说，助手知道这笔钱要审批，却没告诉员工什么时候能订。如果为了评第二项再问一次，它碰巧补上“预订前”，这个分数评的就已经是另一份回答了。

如果这个助手还能代订酒店，验收还要多看一步。即使它回复“请先等审批”，也要翻一下工具调用记录，查查测试环境里的订单。书面批准到达以前，系统有没有真的把房订出去？只读聊天记录，回答不了这个问题。

先拿三句话，看看裁判会怎么判

平台的通用评估器可以选评分模型、写评分提示词，让模型给出 0 到 1 的分数并说明理由。内置模板里有一项文本相似度，适合先看看两份答案说得有多像。但“预订前办妥书面批准”和“预订后办妥书面批准”只差一个字，给员工的建议却正好相反。

给 620 元这道题评“下一步该怎么做”，我会把规则写到业务同事也能直接打分的程度。明确告诉员工要等负责人书面批准后再订，给 1 分。允许先订、只说需要审批，或者回避先后顺序，都给 0 分。裁判还得指出回答里的哪句话支持它的判断。扣了分，就写明助手把哪句话说反了，或者漏了哪个条件。

校准裁判时，我会先请业务同事独立判下面三句，再让模型照同一条规则打分。

助手的回答 按约定该怎么判
“可以先订，回来补批。” 0 分。它明确允许先下单。
“需要审批，记得留票据。” 0 分。它提到了审批，员工依然不知道现在能不能订。
“等负责人书面同意后再订。” 1 分。谁来批、怎样批、什么时候能订，都说清楚了。

如果模型给第二句高分，先读它的理由，看它是不是一看到“审批”就算答对。再把第三句换成“收到负责人的书面同意再下单”，看它会不会因为措辞不同就扣分。遇到人和模型判断不一致，先核对条款，把有歧义的评分规则写清楚，再用留出的样本复验。如果中途换过裁判模型或评分规则，旧版 Agent 也要按新标准重新跑一次，两边的分数才好比较。

换到智能问数，同一条制度还可以出一道有确切答案的题。测试库里放两笔酒店订单，每晚分别是 500 元和 501 元，问“有几笔超标”，答案应该是 1。平台既能把实际 SQL 和参考 SQL 规范化后比较，也能直接核对查询结果。两种 SQL 写法可以查出同样的笔数。要验出把“大于 500”写成“大于等于 500”的错误，就得留着正好 500 元的那笔。多算了它，结果会从 1 变成 2。删掉它，两条查询都会返回 1。

十道题从答对八道变成九道，能上线了吗？

实验跑完，概览里能看到各个评估器算出的平均分和完成条数。点进明细，每道题都有输入、当次实际回答、参考输出，以及对应评估器版本给的分数和理由。碰到 0 分，我会先点开理由。助手答错会丢分，Agent 调用失败或裁判执行失败，平台也会记 0 分，然后继续跑下一题。写验收结果时，我会把调用失败的题也列出来，另记有多少题拿到了有效的回答和评分。超时的题要查调用记录，答错的题要回到制度原文核对，两边都有据可查。

假设新旧两版用同一组十道题、同一个评估器评业务结论。每题只给 0 或 1 分，两次都顺利跑完。把两份结果按题排在一起，会看到这样的变化。

同一道题在两版里的结果 题数
两版都答对 7
旧版答错，新版答对 2
旧版答对，新版答错 1

旧版答对 8 道，新版答对 9 道，平均分从 0.8 涨到了 0.9。但要是新答错的恰好是 620 元那题，员工看到的建议就从“等书面批准”变成了“可以先订”。只看 0.9，看不出这次改动会让人提前下单。

普通 Agent 的实验提供分数和逐题明细，是否上线，要由验收方按事先约好的业务条件决定。如果约定的是“不能引导员工在获批前下单”，我会暂缓上线，从两次实验的明细里找出这道题的原话，核实这次退步。智能问数多了一步自动对比。两个实验都完成、用的也是同一版评测集，就能选旧实验作基线，按通过阈值找出上次通过、这次失败的题，再把选中的题放进错例库。

一周后，怎么复核当时的决定？

一周后有人问“上次为什么暂缓”，我会先打开上次实验，找到 620 元那道题，把当时的回答和评分理由摆出来。如果直接重跑，跑出来的可能已经是另一个结果。

平台给评测集建版本时，记下的是一组样本 ID。同一道题如果被几个版本共用，直接改它的参考答案，几个版本读到的内容都会变。删除这条样本，也会移除各个版本里对它的引用。普通 Agent 跑实验时用的是当时的草稿或已发布配置。只记下评测集版本号，过几天未必找得回同样的题目和应用配置。

为了一周后还能复测，我会在改动前导出这版样本，留好适用条款和裁判版本。跑旧版和新版时，再分别记下各自用的 Agent 配置。把那条关键错例放回相同条件下多跑几次，每次回答和评分都留着。下周再看，能分清究竟是助手改对了，还是制度、题面或评分标准换过了。

最后，我会把三道题分别跑一遍，请验收人替准备订房的员工读一读回答。每晚 620 元，还没获批，助手能不能明确告诉员工先等？把价格改回正好 500 元，它会不会还拦着？价格仍是 620 元，但员工已经拿到书面批准，它还会不会让人再去批一遍？三份回答摆在一起，就能看出助手这次是理清了审批条件，还是碰巧学会了对每个人都说“先等一等”。
