从“聊天写代码”到可控维护：复杂项目的 ADD（锚点驱动开发）落地方案

聊到 Vibe Coding（氛围编程），很多人的第一反应是爽——开个对话框，噼里啪啦一顿输出，半小时就能搓出一个能跑的 Demo。

但只要你真的拿这套方式去维护一个稍微复杂点的中大型项目，不出两周，那种“爽感”就会瞬间变成噩梦。踩过坑的兄弟估计对下面这 5 个场景都深有体会：

  1. 需求彻底失控： 需求文档在飞书里，改动在聊天记录里，代码在仓库里，三者各玩各的。改到最后，连你自己都不知道系统现在的真实逻辑是什么。
  2. UI 疯狂“放飞自我”： 把设计图往 AI 脸上一糊，结果写出来的页面不是少了个弹窗，就是 AI 自己脑补了一堆设计图里根本没有的按钮和卡片。
  3. 测试仓库垃圾成山： 让 AI 补单元测试，它特别热衷于写 1+1=2、测 Getter/Setter、或者自己 Mock 一个返回值再断言它等于这个返回值。代码库迅速膨胀，全是没用的废话。
  4. 核心功能裸奔： 功能写完了，却没有像样的验收测试用例兜底，改一处崩三处，上线全靠祈祷。
  5. 前后端测试形同虚设： 看着满屏绿油油的测试通过，结果一上线就报错。因为全是过度 Mock 出来的“平行宇宙测试”，根本不可信。

为什么 AI 一进复杂项目就容易翻车？说白了，大模型在长上下文和多轮对话中天生患有严重的“注意力涣散症”（ADD）——聊着聊着就忘了最初的约束，写着写着就开始放飞自我。

而治好 AI “注意力涣散”的唯一解药，就是我们今天要聊的这套工程方法论——ADD（Anchor-Driven Development，锚点驱动开发）。

就像 TDD（测试驱动）、DDD（领域驱动）一样，ADD 的核心思想，是在代码仓库里打下四颗坚硬的工程“锚点”（索引锚点、代码反向锚点、视觉边界锚点、验收测试锚点），把飘在半空中的 AI 死死钉在可控的轨道上。你的角色也从“和 AI 聊天写代码的人”，正式切换成架构师、锚点制定者和验收官。

下面就把整套 ADD 工程体系，连同每一个文件的格式、模板、预期效果，以及配套的 6 大核心 Skills 和斜杠指令提示词，毫无保留地拆给你看。

一、 锚点一 & 锚点二：治好“需求偏离”和“Token 爆炸”

AI 写偏，90% 是因为上下文散落各处；而把所有文档全塞给 AI，Token 又会瞬间爆炸，AI 还会因为上下文太长开始“犯傻”。

ADD 的解法是“文档即代码（Docs-as-Code）+ 渐进式披露”——通过索引锚点和代码反向锚点，让 AI 像查字典一样先看目录、再翻具体那一页，绝不让它一口气背完整本字典。

1. 索引锚点：docs/INDEX.md

这是整个项目的“总地图”，必须保持极简（控制在 100 到 200 行以内）。

  • 文件模板：
# 需求文档总索引 · 索引锚点 (docs/INDEX.md)

| 业务领域 | 功能模块 | Spec 文档路径 | 关联核心代码 | UI 清单锚点 | 状态 | 一句话业务说明 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 订单 | 结算与优惠券 | `docs/specs/order/checkout.md` | `src/services/checkout.ts` | `docs/ui-manifest.md#order-checkout` | in-progress | 算价逻辑、优惠券互斥规则、库存预扣 |
| 订单 | 退款与售后 | `docs/specs/order/refund.md` | `src/services/refund.ts` | `docs/ui-manifest.md#order-refund` | draft | 部分退款、原路退回状态机 |
| 支付 | 回调处理 | `docs/specs/payment/webhook.md` | `src/api/webhooks/stripe.ts` | - | implemented | 幂等校验、掉单补偿机制 |
  • 期望达到的效果： 每次开新对话，AI 只需要花极少的 Token 扫一眼这个索引锚点，就能精准定位到目标文档，彻底告别盲目扫描整个 docs/ 目录。

2. 原子化规格文档：docs/specs/<领域>/<功能>.md

千万别把所有需求写在一个几千行的 PRD.md 里！按领域拆成小文件，每个文件死守 300 行以内。而且记住一条铁律：先改 Spec，人工确认没问题，再让 AI 动代码。

  • 文件模板（以 docs/specs/order/checkout.md 为例）：
---
id: order-checkout
tags: [订单, 优惠券, 算价, 库存]
routes: [/checkout, /api/v1/orders/preview]
status: in-progress
---

# 订单结算与算价规格 (Order Checkout)

## 1. 核心业务规则
1. **优惠券互斥：** 满减券与折扣券不可叠加；每次结算最多使用 1 张平台券。
2. **金额兜底：** 优惠抵扣后的实付金额最低为 `0.01` 元（运费不参与商品满减计算）。
3. **库存预扣：** 提交订单时必须校验并锁定实时库存，超时 15 分钟未支付自动释放。

## 2. 数据与接口契约
* `POST /api/v1/orders/preview`
  * 入参：`{ items: Array<{ skuId: string, qty: number }>, couponId?: string }`
  * 出参：`{ subtotal: number, discount: number, shippingFee: number, finalAmount: number }`

## 3. 核心验收标准 · 验收锚点 (Given-When-Then)
* **场景 1（正常算价）：**
  * Given 购物车商品总额 200 元，用户选中一张“满 100 减 20”优惠券
  * When 调用算价接口
  * Then 返回 `discount: 20`，`finalAmount: 180`（不含运费）
* **场景 2（边界值 - 优惠券不满足门槛）：**
  * Given 购物车商品总额 80 元，强行传入“满 100 减 20”优惠券 ID
  * When 调用算价接口
  * Then 接口返回 `400 Bad Request`，错误码 `COUPON_THRESHOLD_NOT_MET`
* **场景 3（异常流 - 库存不足）：**
  * Given SKU-A 实时库存仅剩 1 件，用户请求下单 2 件
  * When 提交订单
  * Then 拒绝创建订单，返回 `409 Conflict`，提示“部分商品库存不足”

3. 代码反向锚点 + 自动巡检脚本

维护老代码时，最怕 AI 改了代码却忘了还有文档。我们在每个核心入口文件（Page、Controller、Service）的第一行，强行打上反向锚点：

// @spec: docs/specs/order/checkout.md
// @ui-manifest: docs/ui-manifest.md#order-checkout

再在仓库 scripts/ 目录下放一个巡检脚本（check_spec_anchors.py），每次提 PR 前自动扫一遍所有代码头部的 @spec 路径是否真实存在。

  • 期望达到的效果： 以后你只需要对 AI 说“帮我改一下 checkout.ts 里的优惠券逻辑”，AI 打开文件第一眼就能顺着反向锚点找到唯一对应的文档，零搜索成本，且文档路径永远不会腐烂失效。

二、 锚点三：治好“UI 幻觉”的视觉边界锚点（ui-manifest.md）

前端开发最头疼的就是“少页、多元素、样式乱飘”。光靠把设计图截屏发给 AI 是不够的，你得用视觉边界锚点锁死结构 + 设计系统锁死样式 + 视觉比对做验收。

视觉边界锚点：docs/ui-manifest.md

  • 文件模板：
# UI 页面与视觉清单 · 视觉边界锚点 (UI Manifest)

> **ADD 执行铁律：**
> 1. 严禁修改、增删本清单未列出的路由或弹窗。
> 2. 严禁自行发明设计稿中不存在的按钮、提示文案或统计卡片。
> 3. 所有样式必须使用 `tailwind.config.ts` 中的 Token，基础组件仅限 `src/components/ui/*`。

---

## 1. 全局页面路由总表（防漏页）

| 页面 ID | 路由路径 | 页面名称 | Figma 节点 / 设计稿 | 关联 Spec | 状态 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `order-list` | `/orders` | 订单列表页 | `figma://file/xxx?node-id=101:2` | `docs/specs/order/list.md` | 已完成 |
| `order-checkout` | `/checkout` | 订单结算页 | `figma://file/xxx?node-id=104:8` | `docs/specs/order/checkout.md` | 开发中 |

## 2. 页面详细规格

### 页面：`order-checkout`（订单结算页）
* **路由：** `/checkout`
* **布局结构：** 桌面端双栏布局（左 8 列：地址与商品；右 4 列：价格汇总吸顶）；移动端单栏堆叠，底部固定支付栏。

#### 必须包含的区块与组件（Strict Checklist）
1. **收货地址卡片 (`AddressCard`)**
   * 展示：收件人姓名、脱敏手机号、省市区详细地址、右侧“切换地址”按钮。
   * **禁止项：** 严禁在此卡片内显示“设为默认”开关。
2. **商品清单 (`OrderItemList`)**
   * 展示：缩略图（64x64）、标题（最多 2 行省略）、规格标签、单价、数量（**纯文本，不可在此页加减数量**）。
3. **价格汇总卡片 (`PriceSummary`)**
   * 展示：商品总额、运费、优惠抵扣、实付金额（加粗主色）、主按钮“提交订单”。

#### 关联弹窗 / 抽屉（防漏交互）
* `AddressSelectDrawer`：点击“切换地址”唤起，右侧滑出抽屉，支持单选。
* `CouponSelectModal`：点击“优惠券”唤起，居中弹窗，仅支持单选，底部带“确认使用”按钮。

#### 必须覆盖的 4 种 UI 状态（防漏边界态）
* **Loading 态：** 算价接口未返回时，右侧显示骨架屏（`Skeleton`），提交按钮置灰。
* **Empty 态（无地址）：** 顶部替换为虚线边框卡片，居中显示 `+ 添加收货地址` 按钮。
* **Error 态（库存不足）：** 顶部弹出 `Alert(variant="destructive")` 提示原因，提交按钮禁用。
* **Submitting 态：** 点击提交后，按钮展示 `Loader2` 旋转图标，文案变为“正在创建订单...”。

#### 验收视觉基线（Playwright 截图比对用）
* Desktop 视口：`1440x900` -> `tests/visual/baselines/checkout-desktop.png`
* Mobile 视口：`375x812` -> `tests/visual/baselines/checkout-mobile.png`
  • 期望达到的效果： 配合 Figma MCP 直接读取节点像素，写完后用 Playwright 自动截一张真实渲染图，把设计图和渲染图一起丢给多模态 AI 做“找茬（Diff）”，彻底治好 UI 幻觉。

三、 锚点四：治好“垃圾单测”的验收测试锚点（Given-When-Then + 去 Mock 化）

为什么你觉得前后端测试像摆设？因为 AI 默认喜欢写孤立的单元测试，而且为了省事，把数据库、网络请求全 Mock 掉了。这种测试测的不是业务，而是“Mock 代码写得对不对”。

ADD 的第四颗锚点，就是把 Spec 里的 Given-When-Then 变成不可篡改的验收测试锚点：

  1. 采用“测试奖杯（Testing Trophy）”策略： 复杂业务里，少写孤立单测，重仓集成测试（Integration）和端到端测试（E2E）。只有纯算法、金额计算这种纯函数才配写单元测试。看到 1+1=2 或测框架默认行为的测试，直接删！
  2. AI 版 TDD（红-绿-重构）： 千万别等业务代码写完了再让 AI “补测试”——那时候它只会顺着自己写错的代码去凑“永远能过”的假测试。正确顺序是：先让 AI 把 Spec 里的 Given-When-Then 写成测试代码（此时运行必挂，红灯） -> 你人工瞄一眼确认用例没漏 -> 再让 AI 写业务代码直到测试变绿。
  3. 彻底去 Mock 化：
  • 后端测试： 严禁 Mock 数据库和 ORM！用 Testcontainers（或本地 Docker 起一个干净的 Postgres/Redis 测试库），直接发真实的 HTTP 请求，把 Router -> Controller -> Service -> DB 整条链路跑通，最后去查数据库里的数据落得对不对。
  • 前端测试： 放弃测组件内部 useState 的无聊测试。核心主流程（登录、下单）用 Playwright 跑真实浏览器，只通过用户看得到的文字和按钮去点；复杂页面交互用 MSW (Mock Service Worker) 在网络层拦截 API。

四、 把规矩写死：双契约文件与 6 大核心 Skills

人会忘，AI 也会忘。必须把 ADD 的四颗锚点沉淀为仓库里的全局契约文件和标准化 Skills（统一放在 .claude/skills/<skill-name>/SKILL.md 目录下）。

1. 全局双契约：CLAUDE.md + AGENTS.md

为了同时兼容 Claude Code、Cursor、Windsurf 和 Codex，建议在根目录同时放 CLAUDE.md 和 AGENTS.md，并在里面写死一条斜杠指令兜底路由，让 /skill-name 在任何编辑器里都能无缝通吃：

# CLAUDE.md / AGENTS.md - ADD（锚点驱动开发）AI 协作铁律

## 1. ADD 四大核心锚点与工作流
- 接到任何任务，**第一步必须先读取 `docs/INDEX.md`（索引锚点）和 `PROGRESS.md`**，定位到具体 Spec 后再按需读取，严禁盲目扫描整个 `docs/` 目录。
- **斜杠指令兜底路由**：当用户输入以 `/<skill-name>`（如 `/spec-architect`、`/drift-auditor`）开头时，若当前编辑器未将其作为原生命令展开，必须第一时间读取 `.claude/skills/<skill-name>/SKILL.md` 并严格按其 SOP 执行。
- 修改代码前，检查文件顶部的 `@spec` 反向锚点；如果业务规则有变，**必须先更新 Spec 文档，经人工确认后再修改代码**。

## 2. 视觉锚点与测试红线
- 开发任何页面前，必须核对 `docs/ui-manifest.md`（视觉边界锚点），严禁自行脑补未提及的按钮、文案或交互。
- **禁止**编写测试类型注解、Getter/Setter 或 `1+1=2` 的无意义单测。
- **禁止** Mock 数据库查询或核心业务逻辑。后端集成测试必须连接真实测试库，前端测试优先使用 Playwright 或 MSW。

2. ADD 体系必备的 6 个核心 Skills

在日常使用时，建议把这 6 个技能按触发方式分成“自动护栏”和“斜杠门禁”两类来用：

  1. /spec-architect（规格架构师 — 门禁类，首行斜杠触发）
  • 何时触发： 新需求启动、大重构前。
  • 做什么： 强制 AI 先读现有代码，然后立下规格锚点和索引锚点，严禁在这个阶段写一行正式业务代码。
  1. ui-fidelity-guard（UI 保真卫士 — 护栏类，可自动伴随触发）
  • 何时触发： 前端页面开发与验收阶段。
  • 做什么： 死盯 ui-manifest.md 视觉边界锚点写页面；写完后调 Playwright 截图，和设计图做视觉比对。
  1. test-strategist（测试策略师 — 护栏类，可自动伴随触发）
  • 何时触发： 编写或 Review 测试代码时。
  • 做什么： 强制执行 Testing Trophy 原则，自动拦截并拒绝无意义的 1+1=2 单测和过度 Mock 的测试。
  1. /bug-investigator（Bug 根因定位专家 — 门禁类，首行斜杠触发）
  • 何时触发： 排查线上或测试环境 Bug 时。
  • 做什么： 严禁 AI 盲猜改代码！强制顺着 @spec 反向锚点定性、定位精确根因、先写一个能稳定复现 Bug 的失败测试（红灯），确认后再动手修复。
  1. /drift-auditor（偏离度审计员 — 门禁类，首行斜杠触发）
  • 何时触发： 功能开发完成、准备提 PR 前。
  • 做什么： 交叉比对四大锚点与 git diff，运行锚点巡检脚本，专门抓“文档写了但代码漏了”以及“代码偷偷加了文档没写的逻辑”。
  1. /context-compressor（上下文压缩器 — 门禁类，首行斜杠触发）
  • 何时触发： 一轮长对话结束、准备开新会话时。
  • 做什么： 把这次对话里敲定的架构决策、踩过的坑、更新过的接口，浓缩成几句话写进 ARCHITECTURE.md 和 PROGRESS.md。

五、 每天直接复制粘贴的 6 个高频提示词（首行斜杠指令版）

客户端通常只在输入文本的最开头（第一行）拦截 / 命令，所以直接把 /skill-name 放在第一行，存进快捷短语里就能开箱即用：

1. 需求对齐与立规格锚点（动手写代码前必发）

/spec-architect
先读一下 `docs/INDEX.md` 索引锚点和 `PROGRESS.md`，找到对应功能的 Spec 文件 `docs/specs/[domain]/[feature].md` 以及相关代码 `[文件路径]`。

现在严禁写任何业务代码。请先给我输出一份实施计划，必须包含：
1. 需要新增或修改的文件清单及各自职责；
2. 涉及的数据结构或 API 契约变更；
3. 基于 Spec 提炼的 5~8 个核心验收场景（Given-When-Then 格式，至少包含 2 个边界值/异常流场景）；
4. 你发现的 Spec 中模糊、遗漏、或者与现有代码冲突的地方。

等我逐项确认后再开始动手。

2. UI 高保真实现与锁视觉锚点（前端开发必发）

/ui-fidelity-guard
参考 `docs/ui-manifest.md` 视觉锚点中的 `[页面ID]` 以及对应的 Figma 节点，实现这个页面。严格遵守以下铁律：
1. 只能使用项目现有的基础组件库和 Design Tokens，严禁硬编码任意色值和魔术像素；
2. 严格还原设计图中的信息层级，严禁自行脑补设计稿和 Manifest 中不存在的按钮、统计卡片、提示文案或交互；
3. 必须完整实现清单中定义的 4 种状态：`Loading`、`Empty`、`Error`、`Submitting`；
4. 文件顶部必须加上 `// @spec` 和 `// @ui-manifest` 反向锚点注释。

写完后，列出你实现的组件清单与状态清单，逐项和 `docs/ui-manifest.md` 核对一遍。

3. 高价值测试生成与锁验收锚点（消灭 1+1=2 垃圾测试）

/test-strategist
为 `[模块/功能]` 编写集成测试 / E2E 测试。避开以下所有红线：
1. 禁止垃圾单测：别写测类型注解、Getter/Setter、常量赋值或 `1+1=2` 的无聊测试；
2. 禁止过度 Mock：后端直接连接真实测试库（Testcontainers），验证 HTTP 状态码 + 响应体 + 数据库真实落库/回滚结果；前端使用 Playwright（仅用 `getByRole` / `getByText`）或网络层拦截；
3. 严格对齐验收锚点：每个测试用例必须直接对应 `docs/specs/[domain]/[feature].md` 中的 `Given-When-Then` 场景；
4. 先确保测试代码能真实捕获逻辑错误（红灯），再让我确认。

4. 提 PR 前的四锚点一致性审计（合并代码前必发）

/drift-auditor
扮演一名极其严苛的 Tech Lead，对比 `docs/specs/[domain]/[feature].md`、`docs/ui-manifest.md` 和当前的 `git diff`，输出 ADD 一致性审计报告：
1. 漏项检查：Spec 里的业务规则、错误码或 UI 4 种边界态，哪些在代码里漏实现了？
2. 越界检查：代码里有没有偷偷混进 Spec 没要求的隐藏逻辑、多余 UI 元素、硬编码或无关重构？
3. 反向锚点巡检：运行 `python3 scripts/check_spec_anchors.py`，确认所有 `@spec` 锚点有效且 `docs/INDEX.md` 已更新；
4. 验收锚点含金量检查：如果我把核心业务里的 `if` 条件取反，新增的测试会全部挂掉吗？

直接给我列出必须整改的清单。

5. Bug 根因定位与回归防线（修 Bug 必发）

/bug-investigator
当前出现以下 Bug：`[粘贴报错日志或复现步骤]`。
不要直接猜着改代码。请按 ADD 4 步处理：
1. 先读取相关代码顶部的 `@spec` 反向锚点，核对属于“实现偏离 Spec”还是“Spec 边界遗漏”；
2. 定位精确根因（精确到文件、函数与条件分支）；
3. 先写一个能稳定复现该 Bug 的失败集成测试/E2E 测试；
4. 修复业务代码（若为需求遗漏先补 Spec），运行全量测试确保变绿且无回归。

6. 长对话结束与上下文压缩（收尾交接必发）

/context-compressor
为本次开发会话做收尾交接：
1. 将本次敲定的关键架构决策提炼为 ADR，追加到 `ARCHITECTURE.md`；
2. 更新 `PROGRESS.md` 的“已完成里程碑”、“已知坑点”和“下一步待办”，删除过时信息（保持 <100 行）；
3. 检查并更新已完成功能的 Spec 状态（`status: implemented`）及 `docs/INDEX.md` 索引锚点。

说到底，复杂项目里的 Vibe Coding，拼的从来不是谁的提示词写得更花哨，而是谁能把资深工程师的经验，转化为仓库里坚硬的四颗工程锚点。只要你用 ADD（锚点驱动开发） 把需求、代码、UI 和测试全部钉死在地面上，AI 就不会再是那个天天给你制造技术债的“注意力涣散实习生”，而会真正变成你手里执行力拉满的王牌工程团队。
