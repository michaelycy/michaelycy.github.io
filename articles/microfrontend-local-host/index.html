微前端与前端基建

微前端子应用怎样单独跑起来

发布于 2021年4月9日

  • 微前端
  • single-spa
  • 本地联调
本文目录
  • 把会员编号留在地址里，把当前组织交给模拟基座
  • 带着同一条详情地址接回真实基座

开发者只启动会员子应用，直接在本地打开一条会员详情地址。地址里有会员编号，页面也挂上去了，第一笔查询却还缺一个条件。平时从 CRM 菜单点进来，主应用已经选好了当前组织。现在只开了一个子应用，这个组织从哪来？

我参与过一套基于 single-spa 的 CRM 基座。忠诚度、数据流和工作台拆成了不同子应用，基座和业务模块通过挂在 window 上的通信桥梁交换信息。我们把基座封装成 npm 包，子应用在自己的开发环境里也能模拟宿主。开发者改一个详情页时，可以先在本地把它挂起来。

把会员编号留在地址里，把当前组织交给模拟基座

拿这条详情地址举例。编号跟着地址走，换一个编号就应该打开另一个会员。组织跟着宿主走，即使地址没变，用户也可能切换组织。若在详情组件里给组织填一个常用的默认值，页面很快就有数据了，开发者却看不出来接回真实基座时第一笔查询会查谁。

可以给本地入口设一个简单的场景。第一次打开详情时，让模拟宿主暂缓给出组织，观察页面能否等到必要条件齐全。随后通过通信桥梁给出测试组织，再看详情请求里的会员编号和组织是否成对出现。第二次用另一个组织打开同一地址，只换宿主提供的数据。这样两个输入各自来自哪里，在请求记录里就看得见。

模拟环境里值得保留的是这段交接。会员详情仍由业务代码解析地址、发查询、处理结果。若让模拟基座顺手返回整页详情，开发者即使把组织传错了，也可能一直看到一张填得很完整的会员卡。

带着同一条详情地址接回真实基座

联调时，把刚才那份子应用接到测试基座，在真实宿主选好同一测试组织，直接打开对应的详情地址。先看基座有没有认出会员模块、把它挂进页面。如果组件已经出现却读不到数据，就对照本地那笔成功请求，查组织何时可用、编号有没有随地址传进来。两边看的都是同一个会员，差异就能落到某一次交接上。

最后从详情切到别的模块，再回到刚才的地址。single-spa 会随应用的激活状态挂载或卸载它，子应用自己注册的监听也需要在卸载时清理。single-spa 应用生命周期说明

此时切一次组织，检查详情收到几次通知、查询带的是哪个组织。假如本地第一次打开时只有一笔查询，接回真实宿主、离开再返回后却发了两笔，就去找上一次离开页面时仍然挂着的监听。
