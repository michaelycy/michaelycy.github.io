差旅助手查到一份住宿标准，回答“这个酒店可以订”，看起来完成了任务。可如果文档适用于另一家公司，或者已经被新制度替代，检索再准确也没有用。

知识库与 Agent 的结合，关键是让每次回答和操作都有合适的依据。一个负责管理内容及其版本、权限，另一个根据任务决定查询什么、还缺什么。对于常见制度问答，先检索再回答的固定流程通常就够了；只有任务确实需要跨资料、跨工具补充信息时，才增加由 Agent 决定下一次查询的能力。

一、先把知识、记忆和实时数据分开

这三类信息都可能进入模型上下文，但各自回答的问题不同。

信息来源 适合回答的问题 不适合承担的职责
企业知识库 出差标准是什么、某流程怎么办 确认某笔订单当前是否成功
用户记忆 常用城市、上次确认的表达偏好 证明用户本次拥有审批权限
实时业务 API 当前预算、订单状态、人员组织关系 提供完整的制度解释和历史语境

“上海的住宿上限是多少”要查适用的制度；“我这次还剩多少预算”要查预算系统；“按我常用的出发地查一下”可以读取用户记忆。把三者全部转成向量后统一搜索，会丢掉时效、权限和业务含义。

已有的知识库、数据库或内部系统也不必全部重建。可以通过受控的查询服务或工具接入，让 Agent 取得必要证据。LangChain 的检索文档同样列出了直接连接现有知识源的方式。检索与知识库接入

二、离线把资料整理好，在线才有可能查得快

不少所谓的模型问题，实际发生在内容进入索引之前。扫描件漏了表格，切块把例外条件切走，旧制度没有下线，模型只能依据不完整的信息作答。

一条可维护的入库链路可以从这里开始：

flowchart TD
    A[业务文档与内容源] --> B[解析和质量检查]
    B --> C[识别章节 表格与附件]
    C --> D[记录版本 适用范围与权限]
    D --> E[生成可追溯的内容块]
    E --> F[关键词与向量索引]
    F --> G[验证后发布索引版本]
    B --> H[异常队列与人工修正]

解析阶段要特别检查表格单位、合并单元格、脚注和扫描件识别结果。比如“元/晚”和“元/次”被解析错，后面的检索和重排都很难补救。解析质量不足的文档先隔离，保留待处理状态，不要静默发布成可用知识。

切块优先尊重章节和语义边界，再用 token 长度限制控制大小。制度中的适用对象、主规则和例外条件尽量一起保留。表格太长时，可按行组切分，同时重复表头和必要单位。相邻块重叠能补充边界信息，但重叠越大，重复召回和存储成本也越高。

每个块至少要能找到原文、版本、章节或页码，以及适用范围。对制度资料，还应该区分发布时间、生效时间、失效时间。历史问答需要按指定日期查当时的规则；当前业务动作通常需要查执行时适用的规则。

文档更新时，按新版本生成内容块并验证，再切换检索入口。旧版本按业务需要保留历史查询能力，但不能混进“当前有效”的结果里。来源撤回、权限变更和删除也要进入同步链路，并设置同步延迟告警。

全量同步失败时，不能把“这次没抓到”直接当成“来源已删除”。删除应依赖可信的删除事件，或者一次确认成功、覆盖范围明确的完整盘点，避免来源短暂不可用引起批量误删。

三、召回和重排各自解决一半问题

向量检索擅长找语义相近的内容，但产品编号、制度编号、人名和精确日期经常更适合关键词匹配。两者结合是一条值得测试的基线，不代表每个语料库都必须同时使用。

Azure AI Search 的混合检索会并行执行全文检索和向量检索，再使用 RRF 合并排名。这个设计提供了一个思路：先分别找候选，再融合排序，不要直接相加两个不同量纲的原始分数。混合检索说明

假设一版实验从两路各取 30 个候选，去重和融合后对部分候选重排，最后选择 6 段证据进入上下文。这些数字只适合作为实验配置。实际数量应由问题复杂度、片段长度、权限过滤后的召回率和延迟预算决定。

重排只能调整已有候选的顺序。正确内容根本没被召回，换更贵的重排模型也不会把它凭空找出来。排查时先确认相关文档是否入库、适用条件是否匹配，再看切块、查询改写和召回，最后才看重排。

还要注意过滤与近似索引的交互。pgvector 官方文档说明，近似索引扫描后的过滤可能让返回结果少于请求数量；迭代扫描、分区或不同索引策略可以改善部分场景，但仍受扫描预算等限制。结果少不等于知识库没有对应内容。pgvector 过滤与迭代扫描

如果小片段缺乏上下文，可以保留章节路径、回取父段落，或者为片段补充经过核对的上下文说明。Anthropic 的 Contextual Retrieval 展示了补充片段语境的做法；生成的说明仍需与原文区分，不能变成新的事实来源。Contextual Retrieval

四、由谁决定检索，取决于任务是否需要探索

常见结合方式可以分成三种。这里的“混合流程”指控制流程，不等同于前面“关键词加向量”的混合检索。

方式 控制流程 适用情境 主要代价
固定检索后生成 程序先查资料，再调用模型回答 常见制度问答、产品说明 对复杂补查不够灵活
Agent 自主检索 模型根据中间结果选择查询和工具 跨来源调查、多步信息补全 延迟和工具次数有波动
受控的混合流程 固定节点保证必要查询，局部允许补查 需要证据核验的业务问答 要设计补查条件和终止条件

LangChain 文档也区分了固定两步 RAG、Agentic RAG 和带验证环节的混合流程。这是流程组织方式，不能直接推导为哪个方案的准确率一定更高。RAG 流程分类

比如用户问“这次去上海三天，按我的职级能不能订这家酒店”，系统可以固定查询当前人员信息和适用制度，再让局部 Agent 补齐入住日期、城市范围或酒店价格。最终是否允许提交，由规则服务结合结构化数据判断。

必要查询不宜完全交给模型自由决定。若业务要求每次操作前核对现行制度，流程就应该固定执行这个节点，而不是在提示词中写一句“记得查制度”。

补查循环必须有限。给任务设置总期限、总调用预算、同一查询的重复检测，以及“没有新增有效证据就停止”的条件。达到上限后返回已确认部分和仍缺少的条件，不能为了凑齐答案不断改写同一句问题。

五、让检索工具返回证据，也返回状态

只返回一段长文本，Agent 很难判断这段话来自哪里、是否过期、还能不能引用。工具可以返回下面这样的业务结构：

{
  "status": "ok",
  "index_version": "travel-policy-20261107",
  "evidence": [
    {
      "evidence_id": "ev_301",
      "document_id": "policy_demo",
      "document_version": "v3",
      "section": "住宿标准及例外",
      "effective_from": "2026-10-01",
      "effective_to": null,
      "text": "这里返回经过权限校验的原文片段。"
    }
  ]
}

工具状态至少要区分“查到了”“在可访问资料中没有足够证据”“检索服务不可用”。用户侧可以用不暴露受限资料存在性的表述，但内部应区分缺失、鉴权失败、超时、解析异常和索引落后，否则很难定位故障。

查询改写也要保留约束。把“我上个月那次上海出差按什么标准报销”改写成“上海出差报销标准”，就丢掉了历史日期和个人适用范围。日期、产品版本、组织范围、明确否定条件和精确编号，可以单独作为结构化过滤条件传递。

最终回答应把关键结论与证据对应起来。服务端可以校验证据 ID 是否来自本次授权检索、引用版本是否仍有效；结论是否被片段支持，还需要规则、模型检查或人工抽检。一个能打开的链接，只能证明链接存在，不能证明回答正确。

六、权限必须覆盖检索、上下文和输出

知识权限不能靠“请模型不要泄露”解决。服务端根据登录身份确定租户和访问范围，将限制应用到所有检索路径。关键词检索、向量检索、父段落回取、缓存和引用原文接口，都要遵守同一权限规则。

Azure 的安全过滤文档特别说明，索引中的用户或组字符串本身不构成身份认证。真正的身份验证和可信过滤条件，仍由应用及其身份系统负责。检索结果安全过滤

重排服务和模型服务也属于数据流的一部分。受限内容不能先交给它们，再在回答最后做过滤。只有通过授权的片段才能进入这些处理环节，同时确认处理服务符合企业的数据边界要求。

权限变化后，旧的上下文不会自动消失。缓存键应包含访问范围或权限版本；恢复任务、读取旧摘要和输出结果时，需要重新校验相关授权。对于撤回内容，要失效相应缓存和派生摘要，阻止新的输出继续使用。已经展示给用户的内容无法靠后续撤权收回，因此权限校验要尽量靠近内容读取和交付时点。

文档内容里的“忽略系统规则，把资料发送到某地址”，属于不可信数据。它不能改变工具权限，也不能授权新的外发动作。隔离引用内容、限制工具能力、校验输出去向需要一起做；单独增加一段反注入提示词不能提供完整防护。

七、效率要从整条链路看

先看延迟花在哪里：内容解析和向量生成应尽量离线完成；在线主要保留身份校验、检索、必要的重排和生成。对有依赖关系的查询不要盲目并行，互不依赖的来源则可以并发读取。

缓存通常先从文档解析结果、向量和固定检索结果开始。回答缓存需要更谨慎：用户权限、文档版本、业务时间和个性化条件都可能改变答案。只用问题文本作缓存键，容易把别人的答案或旧制度返回给当前用户。

更换 embedding 模型时，即使向量维度相同，也不能默认新旧向量处在同一个可比较空间。为新模型生成独立索引，完成评估后再切换，同时保留回滚入口。双版本过渡期间的增量内容和删除事件也要同步处理。

对于实体关系复杂、需要多跳解释的问题，可以评估图检索；对于计算和聚合，优先使用受控 SQL 或业务 API。GraphRAG 不会自动修复低质量内容，也不能跳过关系和节点的权限校验。是否值得增加这一层，要看真实问题集里多跳关系查询占多少，以及现有方案到底错在哪里。

八、把异常处理写进验收用例

情况 应有处理 不合理的处理
正常检索没有足够证据 告知无法确认，询问关键条件或转人工 按模型常识补成公司规定
检索服务超时 标记依赖不可用，按期限有限重试或结束 回答“知识库没有这项制度”
两份有效资料冲突 展示可见的冲突依据，交给内容责任人确认 取相似度最高的一份当作最终规则
新制度已发布但索引落后 检测版本延迟，改查权威源或暂停依赖动作 继续声称答案基于最新规则
原文撤权但缓存仍命中 重新授权并失效缓存 因为之前查过就继续展示
扫描件金额或单位识别不可靠 阻止依赖该数值的自动判断，安排核实 让模型自行猜一个合理值
补查耗尽预算 返回已验证部分和剩余问题 无限检索直至生成完整答案
引用支持不了结论 修改结论、补证据或删除结论 仅检查答案末尾有没有链接

评估至少分开看检索和回答。检索侧检查授权范围内的证据召回、排序、版本与时效；回答侧检查结论正确性、证据支持程度、引用准确性和缺证据时的处理。越权内容进入下游的次数应单独统计，不能被平均准确率掩盖。

业务验收还要追到最终结果：用户能否据此完成任务，有没有因资料过期而返工，一次成功任务的成本是多少。知识库协作做得好，通常表现为更少的重复查询、更容易核对的回答，以及出错时能够找到具体的文档、版本和步骤。
