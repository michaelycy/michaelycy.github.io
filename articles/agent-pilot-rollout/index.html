给客服团队加一个助手，可以先从“根据工单和制度写一份处理草稿”做起。客服照常确认并发出回复。这样能先看到草稿究竟节省了多少时间，也能知道系统最常在哪类工单上弄错。等这些问题清楚了，再决定哪些步骤可以自动化。

先拿现在的做法当基线

挑一个输入、产出和负责人都说得清的任务。以客服工单为例，先确认目前怎样找资料、谁负责判断特殊情况、一次误判会带来多少返工。拉一批脱敏样本，覆盖常见请求、缺资料、政策冲突和必须升级人工的情况。用同一批样本比较现有流程和新方案，记录结果质量、处理时间、人工接管及费用。

原型阶段可以用只读查询和测试数据。做完后先问哪里没有达到要求。缺少可靠知识时，优先补资料；权限太复杂时，先收窄对象范围；错误主要集中在少数类别时，可以直接交给现有流程处理。路径固定的工作继续由程序推进，需要理解自由表达或起草回复的环节再交给模型。 Anthropic 关于工作流和 Agent 的说明

每一步用什么条件放行

阶段 先看哪项结果 出问题怎样退
离线验证 典型任务能完成，权限和异常用例通过 调整范围或回到现有流程
影子对照 用同类输入对照草稿与人工结果 停止镜像，保留差异样本
小范围试用 草稿可用，接管可达，成本在预算内 暂停新任务，切回人工
按范围放量 分组指标稳定，值班与回滚路径可用 按版本或功能开关收回

影子对照只产出用于比较的结果，禁用真实提交、发送和删除。正式灰度按合适的单位固定分组，比如团队或会话，避免一次对话中途切版本。每次放量要同时看样本量和覆盖范围。高频查询很快能看到趋势，低频异常可能需要专门演练。到了预定日期但证据还不够，就维持当前范围。

停止新任务以后，剩下的怎么办

放量前要约定谁来暂停，以及哪些情况立即停。越权访问和重复执行可以作为硬条件，草稿采用率或人工用时则看足够的样本。已有任务分开处理。正在等待审批的，明确由谁接手以及批准是否仍有效。已经调用外部系统但未收到结果的，保留操作编号继续核对。用户还在等结果时，页面给出真实状态与可用入口。

第一阶段如果只能稳定做到“生成草稿，人工确认”，也有可衡量的价值。看看客服实际用了多少草稿，改动集中在哪些字段，再决定下一次投入放在资料治理、回复质量还是自动提交。
