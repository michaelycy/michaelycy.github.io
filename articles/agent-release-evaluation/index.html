一个报销助手给出了正确的余额，文字也很清楚。但它先尝试修改申请，再查余额。要是只给最后一句话打分，这条评测就可能通过。评测集应该写清楚用户要的结果，也要写清楚执行过程允许做什么。

用一个任务把验收条件写完整

拿“查询上个月那次申请的进度”举例。测试环境先准备两张申请，其中一张属于当前员工，另一张属于同部门的其他人。员工用含糊的说法提问时，先确认指的是哪一张。如果请求指向无权查看的申请，预期行为要与系统的权限策略一致。跑完后核对可见结果、实际读取的对象和业务表状态。

要测什么 适合怎么判
访问和写入边界 校验授权结果、调用记录和实际状态变化
业务结论 对照测试数据里的状态与适用规则
引用是否支撑答案 对照原文抽查，必要时用模型做初筛
表达是否清楚 具体评分标准加人工校准

轨迹断言只限定必须发生或严禁发生的动作。只要两条读取路径遵守相同权限、返回相同证据，通常可以允许实现调整。审批和写入场景用隔离测试环境，测试对象可以重置，退款和外发通道用替身或沙箱。多准备一次超时、一次部分成功、一次重复回调，比让 mock 永远返回成功更接近真实使用。 Anthropic Agent 评测实践

裁判分数和硬门槛分开

模型裁判适合初筛自然语言结果。我会把“回答好不好”拆开，让它逐项给出依据，比如日期用错在哪里、哪个结论缺证据。用人工样本检查裁判一致性。做成对比较时交换答案顺序，对不一致的样本再复核。更换裁判模型或评分规则后，用新配置重跑基线，旧分数保留作记录。

越权读取、跳过审批和重复提交应单独阻断发布。回答完整度和表达质量则可以比较同一批样本的变化，必要时重复运行，报告波动范围。题库按常用场景、边界和长尾分组。留一部分题到发版时再看，避免每次改提示词都对着同一组答案调。

先跑哪一批

提交改动时跑确定性检查和小组回归，合并或发版前再跑受影响的场景与关键边界。灰度阶段看真实任务完成、人工接管和单次成功任务成本。样本少时继续观察，点踩率的变化也要结合版本和流量构成判断。

线上坏例可以先把问题重建成可控测试数据，再放进评测集。保留触发失败所需的条件和证据即可。用户原始对话和工具响应有自己的访问与保留规则。
